# Протокол жизненного цикла разработки (DLP)

Неофициальный русский перевод [Development Lifecycle Protocol](https://github.com/edgarjs/dlp), оформленный как скилл. Все документы лежат в `references/`. Читай только те, что нужны текущей фазе.

## Первый ответ на любую задачу

Первый ответ всегда начинается с этого блока, даже если дальше идут вопросы:

> **Путь:** Стандартный / Минимальный / Нужно уточнение, с причиной
> **Ограничения:** что нашёл в README, AGENTS.md/CLAUDE.md и docs проекта (стек, архитектурные решения, стандарты кода), или «ограничений не найдено»
> **Фаза:** ТРЕБОВАНИЯ (стандартный путь) или РАЗРАБОТКА (минимальный)
> **Сквозные аспекты:** что из безопасности, производительности, доступности и наблюдаемости касается задачи, и почему

Потом задай вопросы для настройки сессии:
- куда сохранять артефакты (по умолчанию `docs/`);
- автономность: работать до конца или останавливаться на ревью после каждой фазы;
- уточнения по самой задаче.

## Выбор пути

Подробно: `references/foundations/work-paths.md`.

**Минимальный путь** подходит только для небольшого бага, когда выполнены все условия: изменение изолировано, причина известна, исправление очевидно, риск низкий, изменение обратимо, интерфейсы не меняются, тесты есть или их легко добавить. Тогда сначала напиши обоснование:

> **Обоснование минимального пути:** изолировано в [компонент/файл]; причина: […]; исправление: [одна строка]; риск низкий, потому что […]; обратимо: да; интерфейсы не меняются; тесты: [есть / добавлю]

Если по ходу работы хоть одно условие перестало выполняться, переходи на стандартный путь и скажи почему.

Всё остальное идёт **стандартным путём**: четыре фазы по порядку.

## Фазы

| Фаза | Начни с | Зачем |
|---|---|---|
| ТРЕБОВАНИЯ | `references/requirements/README.md` | Что строим |
| ПРОЕКТИРОВАНИЕ | `references/design/README.md` | Как устроено решение |
| РАЗРАБОТКА | `references/development/README.md` | Строим |
| ТЕСТИРОВАНИЕ | `references/testing/README.md` | Проверяем, что работает |

В каждой фазе: сначала прочитай README фазы, потом документы в порядке, который он задаёт. Сквозные аспекты из шапки сверяй с `references/concerns/` перед каждой фазой. Основы (`references/foundations/`): принципы, термины, принятие решений.

## Сначала артефакты, потом код

Готовь документы до кода, по шаблонам:

| Артефакт | Шаблон | Фаза |
|---|---|---|
| Спецификация требований | `references/templates/requirements-specification.md` | Требования |

## Критерии выхода из фаз

Не переходи дальше, пока не выполнены все пункты.

**Требования → Проектирование**
- [ ] у каждого требования есть понятные критерии приёмки
- [ ] границы охвата записаны
- [ ] заинтересованные лица посмотрели и одобрили
- [ ] неразрешённых неясностей нет

**Проектирование → Разработка**
- [ ] архитектура покрывает все требования
- [ ] модели данных поддерживают все сценарии
- [ ] интерфейсы между компонентами описаны
- [ ] проект прошёл ревью и одобрен
- [ ] документация обновлена

**Разработка → Тестирование**
- [ ] реализация завершена по проекту
- [ ] код-ревью одобрено
- [ ] автоматические проверки проходят
- [ ] известных нерешённых проблем нет

**Тестирование → Готово**
- [ ] у каждого требования есть тест
- [ ] критичные пути покрыты
- [ ] тесты стабильно проходят

## Правила фазы разработки

- Если в проекте нет pre-commit хука, добавь его: он запускает тесты и линтер перед коммитом.
- Выполни `date`: твои знания могут устареть. Версию каждой новой зависимости бери из официального реестра и указывай явно (`references/development/dependency-management.md`).
- Сделал одно и то же дважды — напиши скрипт (`references/development/implementation-workflow.md`).

## Решения и неясности

- Сначала проверь, нет ли ответа в документации проекта. Варианты оценивай по `references/foundations/decision-making.md`.
- Обратимые решения с малым влиянием принимай сам и иди дальше. Необратимые и важные выноси пользователю с вариантами.
- Значимые решения записывай по `references/templates/design-decision.md`.
- Спрашивай, если неясность затрагивает основную функциональность, разные трактовки дают разные реализации или ошибку дорого исправлять. Если неясность мелкая или пользователь недоступен, сделай допущение и запиши его явно.

## Чек-лист сессии

Перед работой: путь выбран, ограничения найдены, фаза названа, README фазы прочитан, аспекты просмотрены.
Перед результатом: артефакты готовы до кода, шаблоны использованы, решения и допущения записаны.
Перед переходом фазы: критерии выхода выполнены, одобрение получено (если работаешь не автономно).

**Напоминание:** самый первый вывод — блок «Путь / Ограничения / Фаза / Сквозные аспекты». Не пропускай его.
