# Контракты API

Определяют интерфейсы между компонентами. API задаёт, что потребители могут запрашивать, что поставщики предоставляют и какие гарантии даются. Контракты формализуют эти соглашения через предусловия, постусловия и инварианты.

> **Обязательный формат:** контракты HTTP API ДОЛЖНЫ документироваться по спецификации OpenAPI 3.1 (формат YAML). В качестве отправной точки используйте шаблон `templates/api-contract.yml`. OpenAPI даёт машиночитаемые контракты, которые позволяют автоматическую валидацию, генерацию документации и клиентских SDK.

## Проектирование операций

Операции — это действия, которые предоставляет компонент.

### Выявление операций

Операции вытекают из требований и архитектуры:

```text
Требование: "Пользователи могут размещать заказы"
Компонент: Order Service

Необходимые операции:
- Создать заказ из корзины
- Получить заказ по ID
- Перечислить заказы пользователя
- Обновить статус заказа
- Отменить заказ
```

### Принципы проектирования операций

**Чёткая цель** — каждая операция делает одно. Её имя отражает цель.

```text
Плохо: process_order(order, action)  — action определяет поведение
Лучше: create_order(order), cancel_order(order_id), ship_order(order_id)
```

**Минимальный интерфейс** — запрашивайте только необходимое; возвращайте только полезное.

```text
Плохо: get_user(id) возвращает весь объект пользователя со всей историей
Лучше: get_user(id) возвращает профиль пользователя; get_user_orders(id) возвращает заказы
```

**Единообразные паттерны** — похожие операции работают похоже.

```text
create_user(user_data) → user
create_order(order_data) → order
create_product(product_data) → product
```

## Входы и выходы

### Проектирование входов

**Обязательные и необязательные** — чётко различайте параметры, которые обязаны быть переданы, и те, у которых есть значения по умолчанию.

```text
create_order(
  user_id,          — обязательный: кто размещает заказ
  items,            — обязательный: что заказывается
  shipping_address, — обязательный: куда доставлять
  notes = null,     — необязательный: особые указания
  priority = normal — необязательный: по умолчанию normal
)
```

**Границы валидации** — определите, какие входные данные допустимы.

```text
user_id: должен быть положительным целым числом, должен ссылаться на существующего пользователя
items: должен быть непустым списком {product_id, quantity}
quantity: должно быть положительным целым числом, максимум 100
```

### Проектирование выходов

**Успешные ответы** — что операция возвращает при успехе?

```text
успешный ответ create_order:
  {
    id: ID только что созданного заказа,
    status: "pending",
    total: рассчитанная итоговая сумма,
    created_at: временная метка
  }
```

**Частичная информация** — возвращайте то, что нужно потребителям, а не всё доступное.

```text
list_orders возвращает сводку: { id, status, total, created_at }
get_order возвращает полные детали: { id, status, total, items, shipping_address, ... }
```

## Спецификация контракта

Контракты делают неявные допущения явными:

- **Предусловия (Preconditions)** — что должно быть истинным до вызова операции
- **Постусловия (Postconditions)** — что будет истинным после завершения операции
- **Инварианты (Invariants)** — что всегда истинно в состоянии компонента
- **Условия ошибок (Error conditions)** — что происходит, когда предусловия не выполнены

### Почему контракты важны

Без контракта:

- Разработчик A предполагает, что get_user возвращает null для отсутствующих пользователей
- Разработчик B предполагает, что get_user выбрасывает исключение
- Баг: код ломается, когда эти предположения встречаются

С контрактом:

- Контракт указывает: get_user возвращает null, если пользователь не существует
- Оба разработчика пишут код против одного и того же ожидания

## Предусловия

Предусловия — это требования, которые должны быть выполнены до вызова операции. Ответственность за их выполнение несёт вызывающий.

```text
Операция: transfer_funds(from_account, to_account, amount)

Предусловия:

- from_account существует и активен
- to_account существует и активен
- amount положительна
- на from_account достаточно средств (balance >= amount)
- from_account и to_account различны
```

### Подходы к проверке предусловий

| Подход | Описание | Когда использовать |
| --- | --- | --- |
| Защитный | Операция проверяет и возвращает ошибки | Публичные API, недоверенные вызывающие |
| Контрактный | Вызывающий обеспечивает; операция предполагает | Внутренние API, доверенные вызывающие |
| Практичный | Проверять критичные; остальным доверять | Большинство ситуаций |

## Постусловия

Постусловия — это гарантии того, что будет истинно после успешного завершения операции.

```text
Операция: transfer_funds(from_account, to_account, amount)

Постусловия (при успехе):

- from_account.balance уменьшился на amount
- to_account.balance увеличился на amount
- Суммарный баланс по обоим счетам не изменился
- Создана запись транзакции с временной меткой

Постусловия (при неудаче):

- Ни один баланс счёта не изменился
- Запись транзакции не создана
- Возвращена ошибка с указанием причины
```

Более сильные постусловия полезнее, но их труднее гарантировать. Указывайте на том уровне детализации, который нужен потребителям.

---

## Инварианты

Инварианты — условия, которые всегда должны быть истинными для компонента или сущности.

```text
Сущность: Order

Инварианты:

- order.total равно сумме значений amount по всем order_items
- order.status — одно из: pending, confirmed, shipped, delivered, cancelled
- order.created_at <= order.updated_at
- если статус 'delivered', то shipped_at задан
- у заказа всегда есть хотя бы один order_item (либо он отменён)
```

Инварианты должны поддерживаться всеми операциями.

## Обработка ошибок

Ошибки — часть интерфейса. Подробные стратегии см. в [error-handling.md](../development/error-handling.md).

### Структура ответа об ошибке

```text
{
  error_type: категория ошибки,
  message: объяснение, понятное человеку,
  details: дополнительный контекст (необязательно),
  field: какое входное поле вызвало ошибку (для ошибок валидации)
}
```

### Ошибка и нарушение предусловия

| Тип | Описание | Пример |
| --- | --- | --- |
| Нарушение предусловия | Вызывающий допустил ошибку (программная ошибка) | `withdraw(account, -50)` |
| Условие ошибки | Допустимый запрос, который нельзя выполнить | `withdraw(account, 100)`, когда баланс 50 |

## Версионирование

API развиваются. Планируйте изменения.

### Когда версионирование важно

Версионирование необходимо, когда потребители внешние, ломающие изменения нарушили бы работу пользователей или должны сосуществовать несколько версий.

Версионирование необязательно, когда все потребители внутренние и могут обновляться вместе.

### Стратегии версионирования

| Стратегия | Пример | Заметки |
| --- | --- | --- |
| URL | `/api/v1/orders` | Самая распространённая, явная |
| Заголовок | `Accept: application/vnd.api.v2+json` | Более чистые URL |
| Параметр | `/api/orders?version=2` | Просто, но менее аккуратно |

### Управление изменениями

**Обратно совместимые** (безопасные): добавление необязательных параметров, новых полей, новых операций.

**Ломающие** (требуют новой версии): удаление полей/операций, изменение типов, изменение обязательных параметров.

## Рекомендации

**Будьте точны** — расплывчатые контракты не являются контрактами.

- Расплывчато: `"Обновляет пользователя"`
- Точно: `"Устанавливает user.email в new_email; устанавливает user.updated_at в текущее время"`

**Будьте полны** — охватывайте все исходы (успех, не найдено, ошибки).

**Будьте реалистичны** — не обещайте то, что не можете гарантировать.

## Типичные ошибки

**Раскрытие внутренней структуры** — API должен отражать понятия предметной области, а не реализацию.

- Плохо: `get_database_row(table, id)`
- Лучше: `get_user(id), get_order(id)`

**Непоследовательное именование** — выберите соглашения и придерживайтесь их.

- Плохо: `getUser, create_order, RemoveProduct`
- Лучше: `get_user, create_order, remove_product`

**«Болтливые» интерфейсы** — необходимость множества вызовов для одной задачи.

- Плохо: `get_order(id)`, затем `get_order_items(id)`, затем `get_shipping(id)`
- Лучше: `get_order(id)` возвращает заказ с позициями и доставкой

## После контрактов API

Когда API и контракты определены:

1. Используйте контракты как авторитетную спецификацию интерфейса
2. Реализуйте так, чтобы удовлетворять контрактам
3. Тестируйте против контрактов (а не только против реализации)
4. Обновляйте контракты при изменении интерфейсов

API — это контракты. Относитесь к изменениям серьёзно и сообщайте о них чётко.
