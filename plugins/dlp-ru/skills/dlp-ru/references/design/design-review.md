# Ревью проекта

Ревью проекта подтверждает, что проект полон, согласован и готов к реализации. Это последний контрольный пункт перед тем, как вкладывать значительные усилия в разработку.

---

## Зачем проводить ревью проекта

Ошибки проектирования, обнаруженные во время реализации, обходятся дорого. Ревью выявляет:

- Пробелы, где требования не охвачены
- Несогласованности между элементами проекта
- Неосуществимые или высокорисковые подходы
- Неясные спецификации, которые вызовут путаницу при реализации
- Упущенные соображения (безопасность, производительность, эксплуатация)

---

## Объём ревью

Ревью проекта охватывает все проектные артефакты:

- Архитектурную документацию
- Спецификации компонентов
- Модели данных
- Определения API
- Контракты интерфейсов
- Ключевые решения и их обоснование

---

## Ревью полноты

Проверьте, что проект охватывает все требования.

### Таблица соответствия

Создайте явное соответствие:

| Требование | Элемент проекта | Заметки |
| --- | --- | --- |
| Пользователь может создавать заказы | OrderService.create | Полностью |
| У заказа есть история статусов | Order.status_history | Полностью |

## Ревью согласованности

Проверьте, что элементы проекта работают вместе без противоречий.

### Согласованность потоков данных

Проследите данные через систему:

**Поток данных: создание заказа**

1. API получает запрос на заказ → проверяет формат
2. OrderService.create → проверяет бизнес-правила
3. Создаёт сущность Order → записывает в OrderRepository
4. Публикует событие OrderCreated → его потребляет NotificationService
5. Возвращает созданный заказ → API форматирует ответ

На каждом шаге проверьте:

- Формат данных соответствует ожиданиям
- Необходимые поля доступны
- Преобразования определены

## Ревью осуществимости

Проверьте, что проект действительно можно реализовать.

### Оценка рисков

Выявите и оцените риски:

```text
Риск: сложность интеграции с платёжным шлюзом
Вероятность: средняя
Влияние: высокое (блокирует оформление заказа)
Снижение риска: спайк для проверки подхода к интеграции до полной реализации

Риск: производительность под нагрузкой
Вероятность: низкая (похожие системы работают хорошо)
Влияние: среднее
Снижение риска: включить нагрузочное тестирование в план тестирования
```

## Процесс ревью

### Подготовка к ревью

Перед ревью:

1. Убедитесь, что все проектные документы завершены
2. Проверьте, что документы согласованы между собой
3. Подготовьте соответствие требованиям
4. Отметьте области неопределённости или беспокойства
5. Определите ревьюеров

### Проведение ревью

Во время ревью:

1. Пройдите по проекту на подходящем уровне детализации
2. Проверьте по чек-листам
3. Прощупайте области, вызывающие беспокойство
4. Задокументируйте все найденные проблемы
5. Классифицируйте проблемы по серьёзности

### Классификация проблем

**Блокер (Blocker)** — должен быть разрешён до начала реализации.

- Пример: `Нет проекта для требуемой системы аутентификации`
- Действие: `Вернуться к проектированию, чтобы закрыть пробел`

**Серьёзная (Major)** — желательно разрешить, но работу можно начинать в незатронутых областях.

```text
Пример: непоследовательный подход к обработке ошибок
Действие: разрешить до реализации затронутых компонентов
```

**Незначительная (Minor)** — нужно отслеживать, но не блокирует прогресс.

```text
Пример: в одном компоненте именование могло бы быть яснее
Действие: учесть при реализации, обновить документацию
```

**Наблюдение (Observation)** — стоит отметить, но не требует действий.

```text
Пример: альтернативный подход мог бы быть проще
Действие: задокументировать для будущего обращения
```

## Чек-лист ревью

```text
Полнота
- [ ] Все требования охвачены
- [ ] Все компоненты специфицированы
- [ ] Все интерфейсы определены
- [ ] Обработка ошибок полна
- [ ] Нефункциональные требования охвачены

Согласованность
- [ ] Нет внутренних противоречий
- [ ] Интерфейсы между компонентами согласуются
- [ ] Потоки данных связны
- [ ] Именование единообразно

Осуществимость
- [ ] Технический подход жизнеспособен
- [ ] Риски выявлены и приемлемы

Качество
- [ ] Проект достаточно прост
- [ ] Компоненты поддерживаемы
- [ ] Проект тестируем

Процесс
- [ ] Ревью проведено
- [ ] Проблемы задокументированы
- [ ] Блокеры разрешены
- [ ] Одобрение зафиксировано
```

## Утверждение

Проект утверждён, когда:

1. Все проверки полноты пройдены
2. Не осталось проблем согласованности
3. Осуществимость подтверждена
4. Качество приемлемо
5. Все блокирующие проблемы разрешены
6. Ревьюеры согласны, что проект готов

### Документирование утверждения

```text
Проект: система управления заказами
Версия: 1.0
Статус: утверждён к реализации
Дата: 2024-01-20
Ревьюеры: [имена/роли]

Незакрытые пункты:
- Незначительный: обновить формат документации API (во время реализации)

Условия:
- Спайк по интеграции платежей должен завершиться до компонента платежей

Заметки:
- Нагрузочное тестирование требуется перед развёртыванием в продакшене
```

---

## После ревью

Когда проект утверждён:

1. Используйте проектные документы как авторитетный источник
2. Относитесь к изменениям проекта как к объектам контроля изменений
3. Начинайте фазу разработки
4. Поддерживайте проектные документы по мере реализации

**Проектные документы остаются живыми артефактами: обновляйте их, когда реализация выявляет необходимые изменения, но отслеживайте такие изменения осознанно.**
