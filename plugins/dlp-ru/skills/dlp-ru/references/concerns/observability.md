# Наблюдаемость

Наблюдаемость (observability) — это способность понимать внутреннее состояние системы по её внешним выходным данным. Она отвечает на вопрос: «Что происходит и почему?»

---

## Образ мышления в наблюдаемости

### Нельзя починить то, чего не видно

Продакшен-системы выходят из строя неожиданными способами. Без наблюдаемости:

- Проблемы обнаруживают пользователи, а не операторы
- Первопричины остаются загадками
- Исправления — это догадки, а не решения

### Три столпа

**Логи (Logs)** — отдельные события, которые произошли.

```text
"User 123 logged in at 10:23:45"
"Payment failed: insufficient funds"
```

**Метрики (Metrics)** — агрегированные измерения во времени.

```text
request_count: 1,523
error_rate: 0.02%
response_time_p95: 245ms
```

**Трассировки (Traces)** — путь запроса через распределённые системы.

```text
Request → API Gateway → Auth Service → Database → Response
         [12ms]        [45ms]         [89ms]
```

Каждый столп отвечает на свои вопросы:

- Логи: что именно произошло?
- Метрики: каково общее состояние здоровья?
- Трассировки: куда ушло время?

## Логирование

### Что логировать

**Логируйте:**

- Сводки запросов/ответов
- Ошибки и исключения
- События аутентификации
- Значимые для бизнеса действия
- Переходы состояний
- Вызовы внешних сервисов

**Не логируйте:**

- Чувствительные данные (пароли, токены, персональные данные)
- Рутинные события большого объёма (в продакшене)
- Избыточную информацию
- Бинарные данные

### Уровни логирования

Используйте уровни последовательно:

| Уровень | Назначение | Пример |
| --- | --- | --- |
| ERROR | Что-то не удалось, требует внимания | Потеряно соединение с БД |
| WARN | Возможная проблема, деградированное состояние | Повтор удался после сбоя |
| INFO | Значимые бизнес-события | Заказ выполнен |
| DEBUG | Подробная диагностическая информация | Попадание/промах кэша |
| TRACE | Очень подробная информация о потоке выполнения | Вход/выход из метода |

- Продакшен: INFO и выше
- Разработка: DEBUG и выше
- Диагностика проблем: TRACE при необходимости

### Структурированное логирование

Используйте структурированные форматы (JSON) вместо обычного текста.

Плохо (обычный текст):

```text
"User 123 failed to login from 192.168.1.1 - invalid password"
```

Лучше (структурированно):

```text
{
  "event": "login_failed",
  "user_id": 123,
  "ip": "192.168.1.1",
  "reason": "invalid_password",
  "timestamp": "2024-01-15T10:23:45Z"
}
```

**Преимущества структурированного логирования:**

- Машиночитаемо
- Поиск по полям
- Возможна агрегация
- Единый формат

### Контекстная информация

Включайте контекст, помогающий отладке:

Необходимый контекст:

- Временная метка (ISO 8601, UTC)
- ID запроса/корреляции
- Идентификатор пользователя/тенанта
- Название сервиса/компонента
- Окружение (prod, staging)

Ситуативный контекст:

- HTTP-метод и путь
- Код статуса ответа
- Длительность
- Детали ошибки

### ID корреляции

Отслеживайте запросы между сервисами с помощью общего ID.

```text
Запрос приходит → Генерируется correlation_id: "abc-123"
  → Сервис A логирует: {correlation_id: "abc-123", ...}
  → Сервис B логирует: {correlation_id: "abc-123", ...}
  → Сервис C логирует: {correlation_id: "abc-123", ...}

Поиск по "abc-123" → виден весь путь запроса
```

## Метрики

### Типы метрик

**Счётчики (Counters)** — значения, которые только растут.

- `http_requests_total`
- `errors_total`
- `orders_completed`

**Измерители (Gauges)** — значения, которые растут и падают.

- `active_connections`
- `queue_depth`
- `memory_usage_bytes`

**Гистограммы (Histograms)** — распределение значений.

- `request_duration_seconds`
- `response_size_bytes`

### Что измерять

**Метод RED (на основе запросов):**

- **R**ate — запросов в секунду
- **E**rrors — неудачных запросов в секунду
- **D**uration — время на запрос

**Метод USE (на основе ресурсов):**

- **U**tilization — процент использования ресурса
- **S**aturation — объём ожидающей в очереди работы
- **E**rrors — события ошибок

### Соглашения об именовании

Используйте последовательные описательные имена:

Формат: `<namespace>_<name>_<unit>`

Примеры:

```text
http_requests_total
http_request_duration_seconds
db_connections_active
queue_messages_pending
cache_hits_total
cache_misses_total
```

### Кардинальность

Будьте осторожны со значениями меток:

Опасно (неограниченная кардинальность):

```text
request_duration{user_id="..."}  // Миллионы пользователей
```

Безопасно (ограниченная кардинальность):

```text
request_duration{endpoint="/users", method="GET", status="200"}
```

Высокая кардинальность резко раздувает расходы на хранение и запросы.

## Распределённая трассировка

### Структура трассировки

```text
Trace: сквозной запрос
  └── Span: API Gateway (12ms)
      └── Span: Auth Service (45ms)
          └── Span: Database Query (30ms)
      └── Span: Order Service (89ms)
          └── Span: Database Query (50ms)
          └── Span: Payment Service (35ms)
```

- **Trace (трассировка)** — полный путь запроса.
- **Span (спан)** — отдельная операция внутри трассировки.
- **Context (контекст)** — передаваемые идентификаторы, связывающие спаны.

### Когда трассировка помогает

- Выявление медленных сервисов в цепочке
- Понимание потока запроса
- Отладка отказов в распределённой системе
- Планирование ёмкости

### Передача контекста

Передавайте контекст трассировки между сервисами:

```text
Сервис A:
  trace_id = generate_trace_id()
  span_id = generate_span_id()
  вызвать Сервис B с заголовками:
    traceparent: "00-{trace_id}-{span_id}-01"

Сервис B:
  извлечь trace_id, parent_span_id из заголовков
  создать дочерний спан, связанный с родителем
```

### Что трассировать

- Входящие HTTP-запросы
- Исходящие HTTP-вызовы
- Запросы к базе данных
- Операции с кэшем
- Операции с очередью сообщений
- Значимые внутренние операции

## Оповещения

### Проектирование оповещений

**Оповещайте о симптомах, а не о причинах:**

- Плохо: оповещение при CPU > 80%
- Лучше: оповещение при времени ответа > 500 мс

CPU может быть высоким, а пользователи — довольны. Время ответа напрямую влияет на пользователей.

**Оповещения, пригодные к действию:**

У каждого оповещения должны быть:

- Чёткое описание проблемы
- Влияние на пользователей/бизнес
- Предлагаемые шаги расследования
- Ссылка на runbook, если применимо

### Уровни оповещений

| Уровень | Значение | Реакция |
| --- | --- | --- |
| Critical | Сервис недоступен, риск потери данных | Немедленный вызов дежурного |
| Warning | Деградация, может стать критичной | Расследовать в ближайшее время |
| Info | Примечательно, но не срочно | Просмотреть в рабочее время |

### Как избежать усталости от оповещений

Проблемы:

- Слишком много оповещений → игнорируются
- Шумные оповещения → потеря чувствительности
- Ложные срабатывания → недоверие

Решения:

- Оповещайте только о состояниях, требующих действий
- Настраивайте пороги на основе данных
- Группируйте связанные оповещения
- Регулярно пересматривайте и чистите оповещения

## Дашборды

### Типы дашбордов

**Обзорный дашборд** — здоровье системы с первого взгляда.

Включите:

- Частоту запросов
- Долю ошибок
- Задержку (p50, p95, p99)
- Активных пользователей/соединений
- Использование ресурсов

**Дашборд сервиса** — глубокое погружение в один сервис.

Включите:

- Метрики, специфичные для сервиса
- Состояние зависимостей
- Недавние развёртывания
- Разбивку ошибок

**Дашборд для расследования** — для поиска и устранения неисправностей.

Включите:

- Детальные разбивки
- Инструменты сравнения
- Интеграцию с логами
- Ссылки на трассировки

### Рекомендации по дашбордам

Делайте:

- Показывайте важное сверху
- Используйте согласованные временные диапазоны
- Включайте контекст (развёртывания, инциденты)
- Давайте ссылки на связанные дашборды

Не делайте:

- Не перегружайте одну страницу
- Не используйте запутанные визуализации
- Не показывайте «метрики тщеславия» (vanity metrics)
- Не допускайте устаревания дашбордов

## Рекомендации по реализации

### Лучшие практики логирования

- Используйте структурированное логирование (JSON)
- Включайте ID корреляции
- Устанавливайте подходящие уровни логов
- Не логируйте чувствительные данные
- Включайте релевантный контекст
- Настройте срок хранения логов

### Лучшие практики метрик

- Следуйте соглашениям об именовании
- Используйте подходящие типы метрик
- Следите за кардинальностью
- Настройте метрики RED/USE
- Определите SLI/SLO

### Лучшие практики трассировки

- Инструментируйте границы сервисов
- Корректно передавайте контекст
- Настройте семплирование в продакшене подходящим образом
- Включайте релевантные атрибуты спанов
- Связывайте трассировки с логами

## Наблюдаемость по фазам

### Фаза требований

- Определите SLI (Service Level Indicators — индикаторы уровня сервиса)
- Установите SLO (Service Level Objectives — цели уровня сервиса)
- Определите критичные пользовательские пути для мониторинга
- Спланируйте аудиторское логирование для соответствия нормам

### Фаза проектирования

- Спланируйте точки инструментирования
- Спроектируйте стратегию ID корреляции
- Спланируйте архитектуру агрегации логов
- Определите ключевые метрики для каждого компонента

### Фаза разработки

- Добавьте логирование в подходящих местах
- Инструментируйте код для метрик
- Добавьте спаны трассировки
- Включайте контекст во всю телеметрию
- Проверьте, что наблюдаемость работает

### Фаза тестирования

- Проверьте, что логи содержат ожидаемую информацию
- Проверьте, что метрики записываются корректно
- Убедитесь, что трассировки правильно связываются
- Протестируйте правила оповещений
- Проведите нагрузочное тестирование инфраструктуры наблюдаемости
