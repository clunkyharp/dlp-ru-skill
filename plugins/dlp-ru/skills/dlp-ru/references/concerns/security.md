# Безопасность

Безопасность защищает системы и данные от несанкционированного доступа, изменения или уничтожения. Это не функция, которую можно добавить позже — её нужно учитывать на каждой фазе.

---

## Образ мышления в безопасности

### Предполагайте взлом (Assume Breach)

Проектируйте системы в расчёте на то, что злоумышленники проникнут внутрь. Ограничивайте ущерб с помощью:

- Эшелонированной защиты (несколько слоёв)
- Наименьших привилегий (минимальный доступ)
- Сегментации (локализация взломов)

### Границы доверия

Определите, где меняется уровень доверия:

- Ввод пользователя (никогда не доверяем)
- Внешние API (проверяем ответы)
- Внутренние сервисы (зависит от архитектуры)
- База данных (доверяем, но защищаем доступ)

Данные, пересекающие границы доверия, должны валидироваться.

## Типичные уязвимости

### Инъекции (Injection)

Недоверенные данные передаются интерпретатору как часть команды или запроса.

**SQL-инъекция**

Уязвимо:

```text
query = "SELECT * FROM users WHERE id = " + user_input
// user_input = "1; DROP TABLE users"
```

Безопасно:

```text
query = "SELECT * FROM users WHERE id = ?"
execute(query, [user_input])  // Параметризованный запрос
```

**Инъекция команд**

Уязвимо:

```text
system("ping " + user_input)
// user_input = "127.0.0.1; rm -rf /"
```

Безопасно:

```text
Использовать библиотеки, не вызывающие оболочку (shell)
Валидировать ввод по списку разрешённого (allowlist)
```

**Предотвращение:**

- Используйте параметризованные запросы/подготовленные выражения
- Избегайте динамического построения команд
- Валидируйте и очищайте весь ввод

### Межсайтовый скриптинг (XSS)

Вредоносные скрипты внедряются в веб-страницы, просматриваемые другими пользователями.

Уязвимо:

```html
<div>Welcome, ${username}</div>
// username = "<script>steal_cookies()</script>"
```

Безопасно:

```html
<div>Welcome, ${escape_html(username)}</div>
```

**Предотвращение:**

- Экранируйте вывод в зависимости от контекста (HTML, JavaScript, URL, CSS)
- Используйте шаблонизаторы с автоматическим экранированием
- Внедрите Content Security Policy (CSP)

### Нарушенная аутентификация (Broken Authentication)

Слабости в механизмах аутентификации.

**Типичные проблемы:**

- Слабые требования к паролям
- Отсутствие защиты от перебора
- Небезопасное управление сессиями
- Учётные данные в URL или логах

**Предотвращение:**

- Требуйте надёжные пароли
- Внедрите ограничение частоты запросов и блокировку аккаунта
- Используйте безопасные токены сессий (случайные, достаточной длины)
- Никогда не логируйте учётные данные или токены

### Нарушенный контроль доступа (Broken Access Control)

Пользователи получают доступ к ресурсам или действиям сверх своих прав.

Уязвимо:

```text
// Пользователь меняет URL с /orders/123 на /orders/456
// Сервер возвращает заказ 456, не проверив владельца
```

Безопасно:

```text
order = get_order(order_id)
if order.user_id != current_user.id:
    return error("Forbidden")
```

**Предотвращение:**

- Проверяйте авторизацию при каждом запросе
- Запрещайте по умолчанию
- Используйте непрямые ссылки (не последовательные ID)
- Логируйте отказы контроля доступа

### Небезопасная конфигурация (Security Misconfiguration)

Небезопасные настройки по умолчанию, неполная настройка или раскрытая информация.

**Типичные проблемы:**

- Не сменены учётные данные по умолчанию
- Включены ненужные функции
- Раскрываются подробные сообщения об ошибках
- Отсутствуют заголовки безопасности

**Предотвращение:**

- Укрепляйте конфигурации (hardening)
- Отключайте неиспользуемые функции
- Показывайте наружу общие сообщения об ошибках
- Внедрите заголовки безопасности

### Раскрытие чувствительных данных (Sensitive Data Exposure)

Недостаточная защита чувствительной информации.

**Предотвращение:**

- Шифруйте данные при хранении и при передаче
- Используйте надёжные современные алгоритмы
- Не храните чувствительные данные без необходимости
- Маскируйте или усекайте в логах и отображении

## Практики безопасного кодирования

### Валидация ввода

Валидируйте весь ввод на границах системы.

Чек-лист валидации:

- [ ] Тип (строка, число, дата)
- [ ] Длина (мин, макс)
- [ ] Формат (regex, структура)
- [ ] Диапазон (допустимые значения)
- [ ] Бизнес-правила

**Список разрешённого лучше списка запрещённого (allowlist over denylist):**

Плохо:

```text
reject if input contains "<script>"  // Легко обойти
```

Лучше:

```text
accept only if input matches [a-zA-Z0-9_]+
```

### Кодирование вывода

Кодируйте вывод в зависимости от контекста, чтобы предотвратить инъекции.

| Контекст | Кодирование |
| --- | --- |
| Тело HTML | HTML-сущности |
| Атрибут HTML | Кодирование атрибутов |
| JavaScript | Кодирование JavaScript |
| Параметр URL | URL-кодирование |
| CSS | CSS-кодирование |

### Аутентификация

**Хранение паролей:**

- Никогда не храните пароли в открытом виде
- Используйте адаптивное хеширование (bcrypt, Argon2)
- Используйте уникальную соль для каждого пароля

**Управление сессиями:**

- Генерируйте случайные ID сессий (достаточная энтропия)
- Пересоздавайте ID сессии при входе
- Устанавливайте подходящий срок действия сессий
- Аннулируйте сессию при выходе

**Многофакторная аутентификация:**

- Внедряйте для чувствительных операций
- Поддерживайте стандартные протоколы (TOTP)

### Авторизация

**Принципы:**

- Наименьшие привилегии (предоставлять минимально необходимое)
- Запрет по умолчанию
- Проверка при каждом запросе
- Безопасный отказ (запрещать при ошибке)

**Реализация:**

Проверка авторизации:

1. Аутентифицировать пользователя (кто он?)
2. Загрузить разрешения (что ему можно?)
3. Проверить конкретное разрешение на действие
4. Отказать, если явно не разрешено

### Криптография

**Делайте:**

- Используйте проверенные библиотеки
- Используйте актуальные алгоритмы (AES-256, SHA-256+, RSA-2048+)
- Используйте аутентифицированное шифрование (режим GCM)
- Генерируйте ключи безопасно

**Не делайте:**

- Не изобретайте собственную криптографию
- Не используйте устаревшие алгоритмы (MD5, SHA1, DES)
- Не зашивайте ключи или секреты в код
- Не используйте предсказуемые IV или nonce

### Управление секретами

**Никогда:**

- Не коммитьте секреты в систему контроля версий
- Не зашивайте секреты в код
- Не логируйте секреты
- Не передавайте секреты в URL

**Делайте:**

- Используйте переменные окружения или менеджеры секретов
- Регулярно ротируйте секреты
- Аудируйте доступ к секретам
- Используйте разные секреты для разных окружений

## Безопасность по фазам

### Фаза требований

- Определите чувствительные данные и операции
- Определите требования к аутентификации
- Определите модель авторизации
- Учтите требования соответствия нормам (GDPR, PCI, HIPAA)
- Явно документируйте требования безопасности

### Фаза проектирования

- Определите границы доверия
- Спроектируйте аутентификацию и авторизацию
- Спланируйте стратегию шифрования
- Рассмотрите модель угроз
- Проверьте безопасность сторонних зависимостей

### Фаза разработки

- Следуйте практикам безопасного кодирования
- Используйте линтеры безопасности и статический анализ
- Проверяйте код на проблемы безопасности
- Поддерживайте зависимости обновлёнными
- Обрабатывайте ошибки, не раскрывая подробностей

### Фаза тестирования

- Включайте тест-кейсы безопасности
- Тестируйте попытки обхода аутентификации
- Тестируйте авторизацию на каждой конечной точке
- Тестируйте валидацию ввода вредоносными данными
- Рассмотрите тестирование на проникновение для критичных систем

## Чек-лист проверки безопасности

### Аутентификация

- [ ] Применяется строгая политика паролей
- [ ] Реализована защита от перебора
- [ ] Безопасное управление сессиями
- [ ] Выход аннулирует сессию
- [ ] Сброс пароля безопасен

### Авторизация

- [ ] Контроль доступа на всех конечных точках
- [ ] Запрет по умолчанию
- [ ] Нет прямых ссылок на объекты без проверок
- [ ] Административные функции защищены
- [ ] Отказы авторизации логируются

### Ввод/вывод

- [ ] Весь ввод валидируется
- [ ] Вывод кодируется под контекст
- [ ] Используются параметризованные запросы
- [ ] Загрузка файлов проверяется и изолируется (sandbox)
- [ ] Нет чувствительных данных в URL

### Защита данных

- [ ] Чувствительные данные зашифрованы при хранении
- [ ] TLS для данных при передаче
- [ ] Секретов нет в коде и логах
- [ ] Минимальный сбор данных
- [ ] Безопасное удаление данных при необходимости

### Конфигурация

- [ ] Учётные данные по умолчанию изменены
- [ ] Ненужные функции отключены
- [ ] Заголовки безопасности внедрены
- [ ] Сообщения об ошибках не раскрывают информацию
- [ ] Зависимости обновлены

## Реагирование на проблемы безопасности

### Когда вы нашли уязвимость

1. **Оцените серьёзность** — какие данные или доступ под угрозой?
2. **Локализуйте** — можно ли быстро ограничить воздействие?
3. **Исправьте** — разработайте и протестируйте исправление
4. **Разверните** — выкатите исправление в продакшен
5. **Проанализируйте** — как это произошло? Как предотвратить подобное?

### Оценка серьёзности

| Серьёзность | Описание | Реакция |
| --- | --- | --- |
| Критическая | Удалённое выполнение кода, неминуемая утечка данных | Немедленное исправление |
| Высокая | Обход аутентификации, раскрытие чувствительных данных | Исправить в течение нескольких дней |
| Средняя | Уязвимость с ограниченным воздействием | Исправить в следующем релизе |
| Низкая | Мелкая проблема, требует маловероятных условий | В бэклог |
