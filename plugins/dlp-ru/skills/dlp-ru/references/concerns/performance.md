# Производительность

Производительность определяет, насколько эффективно система использует ресурсы для выполнения задач. Плохая производительность раздражает пользователей, тратит ресурсы впустую и может приводить к отказам систем под нагрузкой.

---

## Образ мышления в производительности

### Сначала измеряйте

Никогда не оптимизируйте без данных. Интуиция о узких местах часто ошибочна.

Оптимизация без измерений:

```text
"Этот цикл выглядит медленным, оптимизирую его"
Результат: 2 часа потрачено, улучшение 0.1%
```

Оптимизация с измерениями:

```text
Профилирование показывает, что 80% времени уходит на запрос к базе данных
Результат: добавлен индекс, ускорение в 10 раз
```

### Оптимизируйте нужное

Сосредоточьтесь на том, что важно:

- **Горячие пути (hot paths)** — код, который выполняется часто
- **Задержка, видимая пользователю** — то, чего пользователи ждут
- **Ограничения ресурсов** — память, CPU, сеть, хранилище

Не оптимизируйте:

- Код, который выполняется редко
- Различия, которые пользователи не заметят
- Проблемы, которых у вас ещё нет (YAGNI)

### Бюджеты производительности

Задавайте явные лимиты:

- Время загрузки страницы < 2 секунд
- Время ответа API < 200 мс (p95)
- Использование памяти < 512 МБ
- Размер бандла < 200 КБ

Бюджеты делают производительность требованием, а не запоздалой мыслью.

## Типичные проблемы производительности

### База данных

**Запросы N+1** — получение связанных данных по одной записи за раз.

Проблема:

```text
orders = get_all_orders() // 1 запрос
for order in orders:
  order.user = get_user(order.user_id) // N запросов
```

Решение:

```text
orders = get_all_orders_with_users() // 1 запрос с join
// Или пакетно: get_users(order.user_ids) // всего 2 запроса
```

**Отсутствующие индексы** — полные сканирования больших таблиц.

Проблема:

```text
SELECT * FROM orders WHERE user_id = 123
// Сканирует миллионы строк
```

Решение:

```text
CREATE INDEX idx_orders_user_id ON orders(user_id)
// Прямой поиск
```

**Избыточная выборка (over-fetching)** — получение большего объёма данных, чем нужно.

Проблема:

```text
SELECT * FROM users // Возвращает 50 столбцов
// Нужны только name и email
```

Решение:

```text
SELECT name, email FROM users
```

### Память

**Неограниченные коллекции** — загрузка целых наборов данных в память.

Проблема:

```text
all_records = database.get_all() // Миллионы записей
for record in all_records:
  process(record)
```

Решение:

```text
for batch in database.get_in_batches(1000):
  for record in batch:
    process(record)
```

**Утечки памяти** — объекты удерживаются дольше необходимого.

Типичные причины:

- Не удалённые обработчики событий
- Кэши без вытеснения
- Циклические ссылки (в некоторых языках)
- Растущие буферы, которые никогда не очищаются

**Выделение больших объектов** — создание ненужных копий.

Проблема:

```text
data = get_large_data()
copy = data.clone() // Удваивает память
process(copy)
```

Решение:

```text
data = get_large_data()
process(data) // Обрабатывать на месте, если возможно
```

### Сеть

**«Болтливые» протоколы** — слишком много обращений туда-обратно.

Проблема:

```text
get_user(id) // Обращение 1
get_user_orders(id) // Обращение 2
get_user_preferences(id) // Обращение 3
```

Решение:

```text
get_user_with_details(id) // Одно обращение
// Или объединить несколько запросов в пакет
```

**Большие полезные нагрузки (payloads)** — передача большего объёма данных, чем нужно.

Проблема:

```text
API возвращает весь граф объектов
Клиенту нужна только сводка
```

Решение:

```text
Отдельные эндпоинты для сводки и деталей
Или выбор полей (GraphQL, sparse fieldsets)
```

**Отсутствие сжатия** — отправка несжатых данных.

Включите gzip/brotli для:

- Ответов API
- Статических ресурсов
- Больших текстовых нагрузок

### Вычисления

**Избыточные вычисления** — многократное вычисление одного и того же.

Проблема:

```text
for item in items:
  tax_rate = get_tax_rate(region) // Одинаково на каждой итерации
  item.tax = item.price * tax_rate
```

Решение:

```text
tax_rate = get_tax_rate(region) // Один раз
for item in items:
  item.tax = item.price * tax_rate
```

**Неэффективные алгоритмы** — неподходящая сложность для объёма данных.

Проблема:

```text
// Поиск O(n²) в большом списке
for item in large_list:
  if item in another_large_list:
    process(item)
```

Решение:

```text
// O(n) с поиском по множеству
lookup_set = set(another_large_list)
for item in large_list:
  if item in lookup_set:
    process(item)
```

**Блокирующие операции** — синхронное ожидание того, что можно делать параллельно.

Проблема:

```text
result_a = fetch_from_service_a() // Ожидание
result_b = fetch_from_service_b() // Ожидание
// Итого: time_a + time_b
```

Решение:

```text
future_a = async fetch_from_service_a()
future_b = async fetch_from_service_b()
result_a, result_b = await all(future_a, future_b)
// Итого: max(time_a, time_b)
```

## Техники оптимизации

### Кэширование

Сохраняйте вычисленные результаты, чтобы не вычислять заново.

**Уровни кэша:**

- Память приложения (самый быстрый, ограниченный размер)
- Распределённый кэш (общий для экземпляров)
- CDN (статический контент, периферийные узлы)
- Кэш браузера (на стороне клиента)

**Что учесть при кэшировании:**

Вопросы, на которые нужно ответить:

- Что кэшировать? (дорогие или частые операции)
- Как долго? (TTL исходя из требуемой свежести данных)
- Когда инвалидировать? (при обновлении, по расписанию)
- Ключ кэша? (должен однозначно идентифицировать кэшируемый элемент)

**Ловушки кэширования:**

- Устаревшие данные после обновлений
- Cache stampede (много запросов в момент истечения)
- Исчерпание памяти (неограниченный кэш)

### Ленивая загрузка (Lazy Loading)

Откладывайте работу до момента, когда она нужна.

Немедленная, eager (всегда загружается):

```text
user.orders = fetch_all_orders(user.id) // Возможно, никогда не понадобится

Ленивая (загружается при обращении):
user.orders // Загружается только при обращении
```

**Хорошо для:**

- Связанных данных, которые могут не понадобиться
- Дорогой инициализации
- Больших ресурсов (изображения, документы)

**Плохо для:**

- Данных, которые почти всегда нужны (добавляет задержку)
- Ситуаций, где вы создадите запросы N+1

### Пагинация

Обрабатывайте или отображайте данные порциями.

Проблема:

```text
return all_10000_records
```

Решение:

```text
return records[offset:offset+limit]
// С метаданными: total_count, next_page, prev_page
```

**Стратегии пагинации:**

- Offset/limit (просто, медленно при больших смещениях)
- На основе курсора (согласованно, лучше для больших наборов данных)
- Keyset (эффективно, требует сортируемого столбца)

### Денормализация

Обмен места хранения на скорость запросов.

Нормализовано:

```text
Order → OrderItems → Products
// 3 join'а, чтобы получить заказ с названиями товаров
```

Денормализовано:

```text
Order содержит product_name, скопированное из Products
// 1 запрос, но обновления product_name не распространяются
```

**Применяйте, когда:**

- Производительность чтения критична
- Данные меняются нечасто
- Задержка согласованности приемлема

### Асинхронная обработка

Выносите работу с критического пути.

Синхронно:

```text
create_order()
send_confirmation_email() // Пользователь ждёт
update_analytics() // Пользователь ждёт
return response
```

Асинхронно:

```text
create_order()
queue(send_confirmation_email) // В фоне
queue(update_analytics) // В фоне
return response // Пользователь не ждёт
```

**Хорошо для:**

- Некритичных операций
- Операций, которые могут падать независимо
- Работы с непредсказуемым временем выполнения

## Измерение производительности

### Ключевые метрики

**Задержка (Latency)** — время выполнения запроса.

- p50 (медиана) — типичный опыт
- p95/p99 — худшие случаи, которые видит большинство пользователей
- Max — худший случай (часто выбросы)

**Пропускная способность (Throughput)** — запросов, обработанных за единицу времени.

- Запросов в секунду
- Транзакций в минуту

**Использование ресурсов** — какая доля мощности используется.

- Использование CPU
- Использование памяти
- Пропускная способность сети
- Дисковый I/O

**Доля ошибок** — неудачные запросы под нагрузкой.

### Профилирование

Выявляйте, на что уходит время.

**Виды профилирования:**

- Профилирование CPU — какие функции потребляют процессорное время
- Профилирование памяти — что выделяет память
- Профилирование I/O — что ожидает диск/сеть
- Профилирование базы данных — какие запросы медленные

**Подход к профилированию:**

1. Воспроизведите медленный сценарий
2. Запустите профилировщик во время выполнения
3. Определите горячие точки (главные потребители времени)
4. Проанализируйте, необходима ли горячая точка
5. Оптимизируйте или устраните
6. Подтвердите улучшение измерением

### Нагрузочное тестирование

Проверяйте производительность в реалистичных условиях.

**Виды тестов:**

- Базовый (Baseline) — нормальная ожидаемая нагрузка
- Стресс (Stress) — найти точку отказа
- Выдержка (Soak) — длительный прогон для выявления утечек
- Всплеск (Spike) — внезапный рост трафика

## Производительность по фазам

### Фаза требований

- Явно определите требования к производительности
- Определите операции, критичные к производительности
- Задайте измеримые цели (задержка, пропускная способность)
- Учтите ожидаемую нагрузку и рост

### Фаза проектирования

- Выберите подходящие структуры данных
- Спланируйте стратегию кэширования
- Проектируйте с учётом горизонтального масштабирования при необходимости
- Рассмотрите асинхронную обработку для тяжёлых операций
- Проверьте схему базы данных на соответствие шаблонам запросов

### Фаза разработки

- Используйте эффективные алгоритмы и структуры данных
- Избегайте преждевременной оптимизации
- Профилируйте до и после изменений
- Следите за раздуванием зависимостей

### Фаза тестирования

- Включите тесты производительности в CI/CD
- Тестируйте на реалистичных объёмах данных
- Периодически профилируйте во время разработки
- Проводите нагрузочное тестирование перед крупными релизами

## Чек-лист проверки производительности

### База данных

- [ ] Запросы проиндексированы должным образом
- [ ] Нет паттернов запросов N+1
- [ ] Выбираются только нужные столбцы
- [ ] Пагинация для больших наборов результатов
- [ ] Настроен пул соединений

### Кэширование

- [ ] Часто запрашиваемые данные кэшируются
- [ ] Стратегия инвалидации кэша определена
- [ ] Размер кэша ограничен
- [ ] Доля попаданий в кэш мониторится

### Сеть

- [ ] Сжатие включено
- [ ] Минимум обращений туда-обратно
- [ ] Подходящие размеры нагрузок
- [ ] CDN для статических ресурсов

### Код

- [ ] Нет ненужных вычислений в циклах
- [ ] Подходящая алгоритмическая сложность
- [ ] Асинхронность для независимых операций
- [ ] Нет утечек памяти

### Мониторинг

- [ ] Задержка отслеживается (p50, p95, p99)
- [ ] Пропускная способность отслеживается
- [ ] Использование ресурсов отслеживается
- [ ] Оповещения при деградации
