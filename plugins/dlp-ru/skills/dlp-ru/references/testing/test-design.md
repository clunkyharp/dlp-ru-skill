# Проектирование тестов

Проектирование тестов описывает, как писать эффективные, поддерживаемые тесты. Хорошо спроектированные тесты дают уверенность, помогают в отладке и не становятся бременем сопровождения.

---

## Вывод тестов из требований

Тесты должны прослеживаться до требований.

### Из критериев приёмки

Каждый критерий приёмки подсказывает тесты:

Требование: вход пользователя

Критерии приёмки:

- Пользователь может войти с корректными email и паролем
- Пользователь видит ошибку при некорректном email
- Пользователь видит ошибку при неверном пароле
- Аккаунт блокируется после 5 неудачных попыток

Выведенные тесты:

```text
test_login_with_valid_credentials_succeeds
test_login_with_invalid_email_shows_error
test_login_with_wrong_password_shows_error
test_account_locks_after_five_failed_attempts
```

### Из крайних случаев

Требования описывают нормальное поведение; тесты должны покрывать и границы. Полный список типов крайних случаев (пусто/null, границы, специальные значения, варианты состояния) см. в [testing-practices.md](testing-practices.md).

Выводите крайние случаи из требования:

- Требование: расчёт итога корзины покупок
- Крайние случаи: пустая корзина, один товар, очень большие количества, товары с нулевой ценой

### Карта покрытия

Отслеживайте, какие требования имеют тесты:

| Требование | Тест | Статус |
| --- | --- | --- |
| Вход с корректными данными | test_login_succeeds | Покрыто |
| Ошибка неверного email | test_invalid_email_error | Покрыто |
| Блокировка аккаунта | test_account_lockout | Покрыто |
| Сброс пароля | (ещё не реализовано) | Отсутствует |

## Именование тестов

Имена должны описывать, что проверяет тест.

### Принципы именования

**Описывайте сценарий** — какие условия тестируются.

**Указывайте ожидание** — что должно произойти.

**Будьте конкретны** — избегайте общих имён.

### Примеры именования

Плохие имена:

```text
test1
test_login
test_calculate
```

Лучшие имена:

```text
test_login_with_valid_credentials_returns_session_token
test_login_with_expired_password_requires_reset
test_calculate_total_with_discount_applies_percentage
```

### Соглашения об именовании

Выберите соглашение и применяйте его единообразно:

```text
Соглашение: given_when_then
  given_valid_credentials_when_login_then_succeeds

Соглашение: method_scenario_expectation
  login_validCredentials_returnsToken

Соглашение: should_behavior_when_condition
  should_return_token_when_credentials_valid
```

## Структура теста

Используйте единообразную структуру для читаемости. Подробные примеры см. в [testing-practices.md](testing-practices.md).

**Arrange-Act-Assert (AAA)** — подготовить, выполнить действие, проверить результат.

**Given-When-Then** — альтернативная формулировка той же идеи.

Рекомендации:

- Чёткое разделение фаз
- Минимальная подготовка (только то, что нужно этому тесту)
- Одно действие на тест
- Сфокусированные проверки конкретного поведения

## Написание хороших проверок (assertions)

Проверки подтверждают ожидаемые результаты.

### Рекомендации по проверкам

**Будьте конкретны** — по возможности проверяйте точные значения.

- Плохо: `assert result is not null`
- Лучше:
  ```text
  assert result.id == expected_id
  assert result.status == "active"
  ```

**Проверяйте наблюдаемые результаты** — проверяйте то, что код производит, а не как.

- Плохо: `assert internal_counter == 5`
- Лучше: `assert len(result.items) == 5`

**Одна логическая проверка на тест** — несколько assert допустимы, если они проверяют одну концепцию.

Допустимо (одна концепция):

```text
assert user.name == "Alice"
assert user.email == "alice@example.com"
assert user.is_active == true
// Все проверяют, что созданный пользователь корректен
```

Разделить (разные концепции):

```text
test_user_creation_sets_correct_name
test_user_creation_sends_welcome_email
```

### Сообщения проверок

Включайте сообщения, помогающие диагностировать падения:

- Плохо: `assert result == expected`
- Лучше: `assert result == expected, "Expected order total {expected}, got {result}"`

## Тестовые данные

То, как вы создаёте тестовые данные, влияет на качество тестов.

### Принципы тестовых данных

**Минимальные данные** — создавайте только то, что нужно тесту.

- Плохо: создать полного пользователя со всеми 20 заполненными полями, когда тест проверяет только валидацию email.
- Лучше: создать пользователя только с заполненным полем email.

**Очевидные данные** — используйте значения, делающие цель теста понятной.

- Плохо: `test_age_validation with age = 25 // Почему 25?`
- Лучше:
  ```text
  test_under_18_rejected with age = 17 // Явно тестируется граница
  test_18_and_over_accepted with age = 18
  ```

**Изолированные данные** — каждый тест создаёт свои собственные данные.

Плохо:

- Глобальный тестовый пользователь, общий для тестов
- Тесты падают при определённом порядке выполнения

Лучше:

- Каждый тест создаёт нужных ему пользователей
- Тесты независимы

### Паттерны тестовых данных

**Паттерн Builder** — для сложных объектов.

```text
user = UserBuilder()
.with_email("test@example.com")
.with_active_status()
.build()
```

**Фабричные функции** — для типовых объектов.

```text
user = create_test_user(email="test@example.com")
order = create_test_order(user=user, items=3)
```

**Фикстуры (fixtures)** — для общих данных только для чтения.

Используйте фикстуры для:

- Справочных данных (страны, валюты)
- Конфигурации
- Сложных объектов, нужных многим тестам

Избегайте для:

- Данных, которые тесты изменяют
- Данных, которые могут вызвать связанность тестов

## Организация тестов

Организуйте тесты так, чтобы их было легко находить и поддерживать.

### Организация файлов

Вариант 1: повторять структуру исходного кода

```text
src/
  users/user_service.py
tests/
  users/user_service_test.py
```

Вариант 2: группировать по функциям

```text
tests/
  user_registration/
    registration_test.py
    validation_test.py
  user_authentication/
    login_test.py
    password_reset_test.py
```

### Группировка тестов

Группируйте связанные тесты:

```text
UserServiceTests:

test_create_user_with_valid_data
test_create_user_with_duplicate_email_fails
test_create_user_sends_welcome_email

test_update_user_changes_name
test_update_user_with_invalid_email_fails

test_delete_user_removes_from_database
test_delete_user_cancels_pending_orders
```

## Чек-лист проектирования тестов

Покрытие:

- [ ] Требования сопоставлены с тестами
- [ ] Счастливые пути протестированы
- [ ] Крайние случаи протестированы
- [ ] Условия ошибок протестированы

Качество:

- [ ] Тесты независимы
- [ ] Тесты детерминированы
- [ ] Имена тестов описывают сценарии
- [ ] Структура единообразна (AAA или Given-When-Then)

Поддерживаемость:

- [ ] Тесты не зависят от деталей реализации
- [ ] Тестовые данные минимальны и очевидны
- [ ] Тесты логично организованы
- [ ] Упавшие тесты чётко показывают, что сломалось

## Антипаттерны тестов

См. также [testing-practices.md](testing-practices.md) о других типичных ошибках тестирования.

| Антипаттерн | Проблема | Решение |
| --- | --- | --- |
| Test-per-Method (тест на метод) | Тестирует методы, а не поведения | Тестируйте отдельные поведения: `test_calculate_with_discount` |
| Mystery Guest (таинственный гость) | Опирается на данные из другого места | Создавайте данные явно в самом тесте |
| Eager Test (жадный тест) | Проверяет слишком много поведений | Одно поведение на тест |
| Implementation Testing | Ломается при рефакторинге | Тестируйте через публичный интерфейс |
| Slow Tests (медленные тесты) | Разработчики пропускают их запуск | Мокайте медленные зависимости |
| Flaky Tests (нестабильные) | Периодически проходят/падают | См. [test-maintenance.md](test-maintenance.md) |

## Когда тесты трудно писать

Трудность написания тестов часто указывает на проблемы проектирования:

- **Трудно создать объект** — возможно, слишком много зависимостей
- **Трудно проверить результат** — возможно, скрытые побочные эффекты
- **Требуется много мокинга** — возможно, жёсткая связанность
- **Тест сложен** — тестируемый код, возможно, слишком сложен

Рассмотрите рефакторинг кода для улучшения тестируемости.
