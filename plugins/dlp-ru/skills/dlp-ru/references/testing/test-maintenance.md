# Сопровождение тестов

Тестам нужно постоянное сопровождение. Хорошо поддерживаемые тесты остаются ценными; заброшенные тесты становятся обузой. Этот документ описывает, как поддерживать тесты здоровыми с течением времени.

---

## Почему тестам нужно сопровождение

Тесты деградируют по разным причинам:

- **Изменения кода** — изменения реализации могут требовать обновления тестов
- **Изменения требований** — то, что было верным, теперь неверно
- **Изменения окружения** — меняются зависимости, конфигурации или платформы
- **Гниение тестов (test rot)** — тесты со временем становятся нестабильными, медленными или неясными

Заброшенные тесты:

- Дают ложную уверенность (проходят, но не проверяют важное)
- Замедляют разработку (нестабильные падения, медленные запуски)
- Игнорируются (им никто не доверяет)

---

## Когда обновлять тесты

### При изменениях кода

**Поведение изменилось** — тесты должны отражать новое поведение.

- Было: calculate_tax возвращает фиксированные 8%
- Стало: calculate_tax учитывает местоположение пользователя
- Действие: обновить тесты, проверяя новое поведение на основе местоположения

**Интерфейс изменился** — тесты должны использовать новый интерфейс.

- Было: process(item) принимает один элемент
- Стало: process(items) принимает список
- Действие: обновить вызовы в тестах, необязательно меняя намерение теста

**Рефакторинг** — тесты меняться не должны.

- Рефакторинг меняет «как», а не «что».
- Если тесты приходится менять при рефакторинге, значит, они тестировали реализацию.
- Это возможность улучшить качество тестов.

### При изменениях требований

Когда меняются требования, меняются и тесты:

```text
Старое требование: имя пользователя должно содержать 3-20 символов
Новое требование: имя пользователя должно содержать 3-30 символов
```

Действие:

- Обновить граничные тесты (20 → 30)
- Добавить тесты для нового допустимого диапазона (21-30)
- Удалить тесты, проверявшие старое поведение

---

## Когда удалять тесты

Не все тесты стоит хранить вечно.

### Удаляйте тесты, когда

**Код, который они тестируют, удалён** — тесты без тестируемого кода — это мусор.

**Требование удалено** — тесты для устаревших функций сбивают с толку.

**Тест избыточен** — несколько тестов проверяют одно и то же.

**Тест не приносит пользы** — тесты, которые всегда проходят независимо от изменений кода.

### Не удаляйте тесты, когда

**Тест падает** — сначала исправьте или разберитесь; удаление скрывает проблемы.

**Тест неудобен** — неудобные тесты могут ловить реальные проблемы.

**Вы не понимаете, что он проверяет** — разберитесь до удаления.

## Работа с нестабильными тестами

Нестабильные (flaky) тесты — тесты, которые иногда проходят, иногда падают — разрушают доверие к набору тестов.

### Выявление нестабильных тестов

Признаки нестабильности:

- Тест периодически падает в CI
- Тест проходит локально, но падает в CI (или наоборот)
- Тест падает при запуске вместе с другими, но проходит в одиночку
- Результаты теста меняются без изменений кода

### Типичные причины

**Зависимости от времени**

```text
Проблема: тест полагается на завершение операций за определённое время
  assert process_completes_in_under(100ms)

Решение: использовать условия, а не тайминги
  wait_until(process_complete, timeout=10s)
  assert process_status == "complete"
```

**Разделяемое состояние**

```text
Проблема: тесты разделяют данные, которые один из тестов изменяет
  Тест A создаёт пользователя "test@example.com"
  Тест B ожидает, что пользователя с таким email нет

Решение: изолировать тестовые данные
  Каждый тест создаёт данные с уникальными именами
  Каждый тест убирает за собой
```

**Недетерминированное поведение**

```text
Проблема: тест связан со случайностью или текущим временем
  assert generated_id is unique  // Редкая коллизия

Решение: контролировать недетерминизм
  Задавать seed генераторам случайных чисел
  Внедрять время как зависимость
```

**Конкуренция за ресурсы**

```text
Проблема: тесты конкурируют за ограниченные ресурсы
  Тесты запускаются параллельно, все используют порт 8080

Решение: изолировать ресурсы
  Назначать уникальные порты каждому тесту
  Использовать отдельные для каждого теста базы данных
```

### Исправление нестабильных тестов

1. Надёжно воспроизведите (запустите тест много раз, варьируйте условия)
2. Определите причину (тайминги, состояние, ресурсы, недетерминизм)
3. Исправьте первопричину (не просто добавляйте повторы)
4. Проверьте исправление (запустите тест много раз после правки)
5. Наблюдайте (следите за повторным появлением)

## Рефакторинг тестов

Тесты следует рефакторить так же, как продакшен-код.

### Когда рефакторить тесты

**Дублирование** — несколько тестов с похожей подготовкой.

До:

- Каждый тест вручную создаёт пользователя, заказ, платёж

После:

- Вспомогательные функции создают тестовые объекты
- Тесты используют помощников и фокусируются на поведении

**Неясные тесты** — тесты, которые трудно понять.

До:

- `test_1()` с загадочными проверками

После:

- `test_user_with_expired_subscription_cannot_access_premium_content()`

**Медленные тесты** — тесты, которые выполняются слишком долго.

- До: каждый тест запускает свежую базу данных
- После: тесты разделяют подготовку БД, используют транзакции для изоляции

### Рекомендации по рефакторингу

- **Держите тесты проходящими** — рефакторьте небольшими шагами
- **Сохраняйте покрытие** — не теряйте покрытие тестами при рефакторинге
- **Улучшайте ясность** — рефакторинг должен делать тесты понятнее
- **Запускайте часто** — проверяйте, что тесты по-прежнему проходят после каждого изменения

## Метрики здоровья тестов

Отслеживайте здоровье набора тестов:

### Скорость

- Метрика: общее время выполнения набора тестов
- Цель: достаточно быстро, чтобы разработчики запускали тесты часто

Тревожные признаки:

- Разработчики пропускают запуск тестов
- CI занимает слишком много времени
- Тесты со временем замедляются

Действия:

- Профилировать медленные тесты
- Перенести медленные тесты на подходящий уровень
- Распараллелить выполнение тестов
- Оптимизировать подготовку/завершение

### Надёжность

- Метрика: доля нестабильных тестов (падения без изменений кода)
- Цель: ноль нестабильных тестов

Тревожные признаки:

- Тесты игнорируют, потому что «они всегда падают»
- CI требует нескольких повторных запусков
- Разные результаты локально и в CI

Действия:

- Отслеживать и приоритизировать нестабильные тесты
- Исправлять или помещать в карантин до исправления
- Не сливать код с известными нестабильными тестами

### Покрытие

- Метрика: процент покрытия кода
- Цель: соответствующая уровню риска (см. test-strategy.md)

Тревожные признаки:

- Покрытие со временем падает
- Критичные пути не покрыты
- Театр покрытия (высокие цифры, слабые тесты)

Действия:

- Просматривать покрытие при код-ревью
- Добавлять тесты для нового кода
- Фокусироваться на осмысленном покрытии, а не на цифрах

### Нагрузка по сопровождению

- Метрика: время, затрачиваемое на сопровождение тестов
- Цель: устойчивое; не подавляющее время разработки

Тревожные признаки:

- Тесты часто ломаются при изменениях кода
- Значительное время на починку тестов вместо написания функций
- Разработчики боятся менять тесты

Действия:

- Улучшать проектирование тестов
- Тестировать поведение, а не реализацию
- Снижать хрупкость тестов

## Чек-лист здоровья тестов

### Регулярный обзор

- [ ] Все тесты стабильно проходят
- [ ] Нет известных нестабильных тестов (или ими занимаются)
- [ ] Набор тестов выполняется за приемлемое время
- [ ] Покрытие на целевом уровне
- [ ] Тесты понятны

### При изменении тестов

- [ ] Тест по-прежнему проверяет задуманное поведение
- [ ] Имя теста отражает текущее поведение
- [ ] Тестовые данные минимальны и очевидны
- [ ] Тест стабилен (не является flaky)

### Периодическая проверка здоровья

- [ ] Удалить тесты для удалённого кода
- [ ] Обновить тесты для изменённых требований
- [ ] Исследовать и исправить нестабильные тесты
- [ ] Пересмотреть и улучшить медленные тесты
- [ ] Сверить покрытие с целями

---

## График сопровождения набора тестов

**С каждым изменением:**

- Запускать релевантные тесты
- Обновлять тесты, если поведение изменилось
- Убедиться, что у нового кода есть тесты

**Еженедельно:**

- Просматривать падения тестов
- Заниматься нестабильными тестами
- Следить за временем выполнения тестов

**Ежемесячно:**

- Оценивать общее здоровье тестов
- Чистить устаревшие тесты
- Сверять покрытие с целями

**Ежеквартально:**

- Всесторонний обзор набора тестов
- Рефакторить проблемные области
- Обновлять стратегию тестирования при необходимости

---

## Признаки проблем с набором тестов

| Симптом | Возможная причина | Действие |
| --- | --- | --- |
| Тесты игнорируются | Нестабильные или медленные тесты | Улучшить надёжность, скорость |
| Тесты всегда проходят | Слабые проверки | Усилить тесты |
| Тесты всегда падают | Сломаны тесты, а не код | Исправить или удалить тесты |
| Страшно менять код | Хрупкие тесты | Улучшить проектирование тестов |
| Баги в продакшене | Не хватает тестов | Улучшить покрытие |
| Медленная разработка | Слишком много тестов | Привести набор тестов к разумному размеру |
