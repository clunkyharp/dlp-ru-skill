# Фаза тестирования

Проверьте, что реализация соответствует требованиям и проекту. Тестирование подтверждает, что построенное работает корректно и продолжает работать по мере развития системы.

---

## Краткое описание фазы

| Аспект | Детали |
| --- | --- |
| **Цель** | Убедиться, что решение работает корректно |
| **Условия входа** | Реализованный и прошедший ревью код |
| **Условия выхода** | Проверенный код с проходящим набором тестов |
| **Ключевые артефакты** | Набор тестов, отчёты о покрытии, тестовая документация |

---

## Назначение

Тестирование отвечает на вопрос: «Делает ли ПО то, что должно?»

Без адекватного тестирования:

- Баги доходят до пользователей
- Изменения ломают существующую функциональность
- Уверенность в системе падает
- Разработка замедляется, поскольку растёт страх перед изменениями

## Входы и выходы

**Входы:**

- Реализованный и прошедший ревью код
- Спецификация требований
- Контракты интерфейсов
- Проектная документация

**Выходы:**

- Проверенный, протестированный код
- Набор тестов для постоянной верификации
- Задокументированное покрытие и известные ограничения

```mermaid

    A[Реализация] --> B[Стратегия тестирования]
```

Тестирование — непрерывный процесс: оно начинается во время разработки и продолжается на протяжении всей жизни системы.

## Ключевые принципы

- **Тестируйте поведение, а не реализацию** — тесты проверяют, что делает код, а не как он это делает
- **Быстрая обратная связь** — тесты должны выполняться быстро, чтобы их запускали часто
- **Изоляция** — тесты не должны влиять друг на друга; падение одного не должно каскадом вести к другим
- **Детерминизм** — тесты дают одинаковые результаты при каждом запуске
- **Ясность** — падение теста должно чётко указывать, что не так

## Уровни тестирования

Разные тесты служат разным целям:

**Модульные тесты (unit)** — проверяют отдельные компоненты в изоляции.

- Быстрые, сфокусированные, их много
- Ловят баги в логике компонента
- Запускаются при каждом изменении

**Интеграционные тесты (integration)** — проверяют совместную работу компонентов.

- Медленнее, шире по охвату
- Ловят проблемы на границах
- Запускаются регулярно

**Сквозные тесты (end-to-end, E2E)** — проверяют полные рабочие сценарии.

- Самые медленные, охватывают всю систему
- Ловят проблемы интеграции
- Запускаются перед релизами

## Покрытие тестами

Покрытие показывает, какой код выполняется тестами, а не качество тестов.

**Высокое покрытие при плохих тестах** — код выполняется, но проверки слабые.

**Низкое покрытие при хороших тестах** — критичные пути протестированы хорошо; остальное игнорируется.

Стремитесь к осмысленному покрытию:

- Критичные пути: высокое покрытие
- Крайние случаи: тестируются явно
- Обработка ошибок: проверена
- Тривиальный код: тесты могут не требоваться

## Чек-лист выхода: когда тестирование завершено

Выполните ВСЕ пункты, чтобы считать проект проверенным:

- [ ] Для всех требований есть соответствующие тесты
- [ ] Критичные пути тщательно покрыты
- [ ] Крайние случаи и условия ошибок протестированы
- [ ] Тесты стабильно проходят
- [ ] Есть уверенность, что изменения не сломают функциональность незаметно
- [ ] Документация обновлена

Тестирование никогда не бывает по-настоящему завершённым — оно развивается вместе с системой.

## Сквозные аспекты для учёта

При тестировании учитывайте:

- **Безопасность** (`concerns/security.md`) — тестируйте аутентификацию, авторизацию, уязвимости к инъекциям
- **Производительность** (`concerns/performance.md`) — проводите нагрузочное тестирование критичных путей, проверяйте время ответа
- **Доступность** (`concerns/accessibility.md`) — тестируйте с помощью вспомогательных технологий
- **Наблюдаемость** (`concerns/observability.md`) — проверяйте, что логирование и метрики работают корректно
