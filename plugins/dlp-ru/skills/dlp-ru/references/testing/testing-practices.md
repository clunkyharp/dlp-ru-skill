# Практики тестирования

Практики модульного и интеграционного тестирования для проверки отдельных компонентов и их взаимодействия.

---

## Модульное тестирование

Модульные тесты проверяют отдельные компоненты в изоляции. Они составляют основу пирамиды тестирования, обеспечивая быструю обратную связь о корректности компонентов.

### Что делает модульный тест хорошим

| Качество | Описание |
| --- | --- |
| **Быстрый** | Выполняется за миллисекунды, без I/O |
| **Изолированный** | Нет разделяемого состояния, можно запускать параллельно |
| **Детерминированный** | Одинаковый ввод — одинаковый вывод, без случайных падений |
| **Сфокусированный** | Одно поведение на тест |

### Структура Arrange-Act-Assert

```text
test "calculates order total correctly":
  // Arrange: подготовить тестовые данные
  order = create_order()
  order.add_item(product_a, quantity=2, price=10.00)
  order.add_item(product_b, quantity=1, price=25.00)

  // Act: выполнить тестируемое действие
  total = order.calculate_total()

  // Assert: проверить ожидаемый результат
  assert total == 45.00
```

- **Arrange (подготовка)** — создайте объекты, настройте моки, подготовьте входные данные (минимально)
- **Act (действие)** — выполните единственное тестируемое действие (обычно одна строка)
- **Assert (проверка)** — проверьте ожидаемый результат (сфокусированно на том, что проверяет этот тест)

## Тестовые дублёры (Test Doubles)

Используйте тестовые дублёры, когда реальная зависимость медленная, недетерминированная, имеет побочные эффекты или трудна в настройке.

| Тип | Назначение | Когда использовать |
| --- | --- | --- |
| **Stub** | Возвращает заранее заданные значения | Нужны конкретные данные, число вызовов не важно |
| **Mock** | Проверяет, что взаимодействия произошли | Само взаимодействие И ЕСТЬ поведение (например, уведомления) |
| **Fake** | Рабочая упрощённая реализация | Стабы слишком сложны, нужно реалистичное поведение |

### Рекомендации по использованию

- Предпочитайте стабы мокам — проверять выходные данные надёжнее, чем проверять вызовы.
- Держите фейки простыми — сложные фейки становятся бременем сопровождения.
- Мокайте на границах — мокайте внешние системы, а не внутренних коллабораторов.
- Избегайте глубокого мокинга — если мокинг требует много уровней, тестируйте на другом уровне.

## Крайние случаи для тестирования

### Типичные сценарии

| Категория | Примеры |
| --- | --- |
| Пусто/Null | Пустые коллекции, null-значения, отсутствующие необязательные параметры |
| Границы | Мин/макс допустимые значения, чуть ниже/выше пределов, ноль, отрицательные |
| Специальные значения | Очень большие/малые значения, спецсимволы, юникод |
| Варианты состояния | Первый/последний элемент, один vs. несколько, уже в целевом состоянии |

## Интеграционное тестирование

Интеграционные тесты проверяют, что компоненты корректно работают вместе. Они ловят проблемы на границах между компонентами.

### Что проверяют интеграционные тесты

- **Взаимодействие компонентов** — компоненты корректно общаются
- **Поток данных** — данные корректно передаются между компонентами
- **Соблюдение контрактов** — компоненты придерживаются своих интерфейсов
- **Интеграция с инфраструктурой** — код работает с реальными базами данных, API

### Модульные и интеграционные тесты

| Аспект | Модульные тесты | Интеграционные тесты |
| --- | --- | --- |
| Охват | Один компонент | Несколько компонентов |
| Скорость | Миллисекунды | Секунды |
| Зависимости | Моки/стабы | Реальные или реалистичные |
| Что ловят | Логические ошибки | Ошибки интеграции |
| Количество | Много | Меньше |

---

## Реальные зависимости и тестовые дублёры

**Используйте реальные зависимости, когда:**

- Вы тестируете саму интеграцию (в этом и суть)
- Вы тестируете запросы к базе данных (нужно поведение реальной БД)
- Тестовые дублёры было бы сложно поддерживать

**Используйте тестовые дублёры, когда:**

- Внешний сервис ненадёжен, медленный или имеет побочные эффекты
- Настроить реальный сервис непрактично
- Нужно протестировать сценарии ошибок, которые трудно получить с реальным сервисом

## Интеграция с базой данных

| Подход | Преимущества | Недостатки |
| --- | --- | --- |
| БД в памяти | Быстро, очистка не нужна | Может отличаться от продакшена |
| Тестовый экземпляр БД | Поведение как в продакшене | Медленнее, требует настройки |

### Рекомендации по тестированию БД

- Подготовка: создавайте чистую схему или используйте откат транзакции
- Изоляция: тесты не должны зависеть от порядка; очищайте за собой
- Скорость: минимизируйте операции, используйте транзакции для отката

## Интеграция с API

### Тестирование ваших API

Тестируйте:

- Корректные ответы на валидные запросы
- Ответы с ошибками на невалидные запросы
- Аутентификацию и авторизацию
- Типы содержимого, заголовки, коды статуса

Подход:

- Используйте тестовый клиент, выполняющий реальные HTTP-запросы
- Тестируйте через HTTP-слой, а не вызывая обработчики напрямую

### Тестирование внешних API

| Подход | Описание |
| --- | --- |
| Мок-клиент | Быстро, контролируемо; может пропустить изменения API |
| Песочница/тестовая среда | Реальное поведение; может быть медленно/с лимитами |
| Запись/воспроизведение (record/replay) | Баланс реального поведения и скорости |

## Тестирование границ

Сосредоточьте интеграционные тесты на границах компонентов.

Тестирование границы между OrderService и PaymentGateway:

```text
test "order service handles payment timeout":
  // Arrange
  payment_gateway = create_slow_payment_gateway(timeout_after=30s)
  order_service = OrderService(payment_gateway)
  order = create_test_order()

  // Act
  result = order_service.process_payment(order)

  // Assert
  assert result.status == "payment_failed"
  assert result.error.type == "timeout"
  assert order.status == "pending"  // Не изменён на paid
```

## Управление тестовой средой

### Подготовка среды

Перед тестами:

- Запустите необходимые сервисы (база данных, очередь сообщений)
- Создайте схемы/таблицы
- Настройте подключения

После тестов:

- Очистите тестовые данные
- Освободите подключения
- Остановите сервисы (если они запускались для тестов)

### Управление тестовыми данными

- Каждый тест создаёт то, что ему нужно
- Тесты не разделяют изменяемые данные
- Тесты убирают за собой
- Используйте откат транзакции для быстрой очистки

## Чек-листы

### Модульные тесты

- [ ] Тест быстрый (миллисекунды)
- [ ] Тест изолирован (нет разделяемого состояния)
- [ ] Тест детерминирован (один и тот же результат каждый раз)
- [ ] Тест сфокусирован (одно поведение)
- [ ] Структура Arrange-Act-Assert ясна
- [ ] Счастливый путь, крайние случаи и условия ошибок протестированы

### Интеграционные тесты

- [ ] Тестовая среда настроена
- [ ] Зависимости доступны (база данных, сервисы)
- [ ] Тесты фокусируются на интеграции, а не на логике модулей
- [ ] Тесты проверяют взаимодействие компонентов
- [ ] Тесты обрабатывают сценарии ошибок
- [ ] Тесты убирают за собой
- [ ] Тесты надёжны (без нестабильности, flakiness)

## Типичные ошибки

| Ошибка | Плохо | Лучше |
| --- | --- | --- |
| Тестирование реализации | Проверять внутренние вызовы | Проверять выходные данные, тестировать публичный интерфейс |
| Слишком много подготовки | 50 строк setup | Минимальная подготовка, использовать билдеры |
| Много проверок | Проверять 10 вещей | Один тест на сценарий |
| Недетерминизм | Использовать текущее время | Внедрять время, контролировать seed |
| Медленные тесты | Сетевые вызовы | Мокать медленные зависимости |
| Слишком много в тесте | Интеграционные тесты, проверяющие логику | Тестировать логику в модульных тестах |
| Нестабильные тесты (flaky) | Иногда проходят, иногда падают | См. [test-maintenance.md](test-maintenance.md) |

## Когда не нужно писать модульные тесты

Некоторому коду модульные тесты могут не требоваться:

- **Тривиальный код** — простые геттеры, базовое делегирование
- **Сгенерированный код** — код, созданный инструментами
- **Конфигурация** — статическая конфигурация без логики
- **Тонкие обёртки** — код, который просто вызывает другой API

Такой код часто лучше проверять интеграционными тестами, код-ревью или статическим анализом.
