# Обработка ошибок

Как ПО реагирует, когда что-то идёт не так. Хорошая обработка ошибок делает системы устойчивыми и отлаживаемыми.

---

## Категории ошибок

Разные ошибки требуют разных стратегий обработки.

### Восстановимые и невосстановимые

**Восстановимые ошибки** — операция не удалась, но система может продолжать.

Примеры:

- Некорректный ввод пользователя
- Тайм-аут сети (можно повторить)
- Файл не найден (можно спросить пользователя)
- Недостаточно прав

**Невосстановимые ошибки** — система не может безопасно продолжать.

Примеры:

- Нехватка памяти
- Повреждение критичных данных
- Отсутствие необходимой конфигурации
- Программные ошибки (баги)

### Ожидаемые и неожиданные

**Ожидаемые ошибки** — известные режимы отказа, являющиеся частью нормальной работы.

Примеры:

- Пользователь вводит email в неверном формате
- Платёж отклонён
- Ресурс временно недоступен

**Неожиданные ошибки** — сбои, которых не должно быть при нормальных обстоятельствах.

Примеры:

- Нулевой указатель там, где null невозможен
- Недопустимое состояние, которое должны предотвращать инварианты
- Сторонняя библиотека выбрасывает недокументированное исключение

## Стратегии обработки

### Падать быстро (Fail Fast)

Обнаруживайте ошибки как можно раньше и немедленно прекращайте обработку.

Пример Fail Fast:

```text
process_order(order):
  if order is null:
    raise Error("Order cannot be null")
  if order.items is empty:
    raise Error("Order must have items")
  // Теперь мы знаем, что заказ корректен
```

**Когда использовать:** для нарушений предусловий и программных ошибок.

**Выгода:** ошибки ловятся рядом с источником, что упрощает отладку.

### Плавная деградация (Graceful Degradation)

Продолжайте работать с урезанной функциональностью вместо полного отказа.

Пример плавной деградации:

```text
get_user_profile(user_id):
  profile = fetch_basic_profile(user_id)  // Обязательно

  try:
    profile.recommendations = fetch_recommendations(user_id)
  catch NetworkError:
    profile.recommendations = []  // Продолжаем без рекомендаций

  return profile
```

**Когда использовать:** для некритичных функций, где частичный результат лучше, чем отсутствие результата.

**Выгода:** система остаётся полезной, даже когда часть её отказывает.

### Повтор с нарастающей задержкой (Retry with Backoff)

При временных сбоях повторяйте операцию с нарастающими задержками.

Пример повтора:

```text
fetch_with_retry(url, max_attempts=3):
  for attempt in 1 to max_attempts:
    try:
      return fetch(url)
    catch TransientError:
      if attempt == max_attempts:
        raise
      wait(exponential_backoff(attempt))
```

**Когда использовать:** для сетевых запросов и временных сбоев инфраструктуры.

**Что учесть:** ограничивайте число повторов; используйте экспоненциальную задержку между повторами; помните об идемпотентности.

### Значения по умолчанию (Fallback)

Предоставляйте значения по умолчанию, когда предпочтительный источник недоступен.

Пример fallback:

```text
get_configuration(key):
  try:
    return config_service.get(key)
  catch ServiceUnavailable:
    return default_values[key]  // Откат к встроенным значениям по умолчанию
```

**Когда использовать:** когда существует разумное значение по умолчанию, и оно лучше отказа.

**Риск:** молчаливое использование fallback может маскировать проблемы. Логируйте, когда fallback используется.

## Распространение ошибок

Когда компонент сталкивается с ошибкой, он должен решить: обработать её или пробросить выше.

### Когда обрабатывать

Обрабатывайте ошибки, когда:

- Можно осмысленно восстановиться
- У вас есть контекст для подходящей обработки
- Проброс потерял бы важную информацию
- Ошибка ожидаема на этом уровне

### Когда пробрасывать

Пробрасывайте ошибки, когда:

- Нельзя осмысленно восстановиться
- У более высокого уровня больше контекста для обработки
- Ошибка указывает на проблему за пределами вашей зоны ответственности

### Преобразование ошибок

При пробросе подумайте о преобразовании ошибки:

```text
Нижний уровень выбрасывает: DatabaseConnectionError
Верхний уровень перехватывает и преобразует:
  "Cannot process order: database unavailable"
```

Зачем преобразовывать:

- Скрыть детали реализации (пользователя не волнует база данных)
- Добавить контекст (какая операция не удалась)
- Привести к подходящему уровню абстракции

Сохраняйте исходную ошибку как причину для отладки:

```text
catch DatabaseConnectionError as e:
  raise OrderProcessingError("Cannot process order", cause=e)
```

## Пользовательские и внутренние ошибки

Ошибки, показываемые пользователям, отличаются от ошибок, логируемых для разработчиков.

### Ошибки для пользователей

Сообщения об ошибках для пользователей должны быть:

**Полезными** — говорить пользователю, что пошло не так и что с этим делать.

- Плохо: `"Error 500"`
- Лучше: `"We could not process your payment. Please check your card details and try again."`

**Нетехническими** — избегайте жаргона, стек-трейсов и деталей реализации.

- Плохо: `"NullPointerException in OrderService.java:142"`
- Лучше: `"Something went wrong. Please try again or contact support."`

**Безопасными** — не раскрывайте информацию, которая может помочь злоумышленникам.

- Плохо: `"Invalid password for user admin@example.com"`
- Лучше: `"Invalid email or password" // Не подтверждает, что пользователь существует`

### Внутренние ошибки

Внутренняя информация об ошибках должна быть:

**Подробной** — включайте всё необходимое для диагностики проблемы.

```text
Лог: ERROR 2024-01-15 10:23:45 OrderService.process
     Order processing failed for order_id=12345, user_id=67890
     Cause: PaymentGatewayTimeout after 30000ms
     Request ID: abc-123-def
     Stack trace: ...
```

**Контекстной** — включайте релевантное состояние и идентификаторы.

**Структурированной** — используйте единый формат для автоматического анализа.

## Отчётность об ошибках

### Логирование

Логируйте ошибки с достаточным контекстом:

Чек-лист логирования:

- [ ] Временная метка
- [ ] Уровень серьёзности (error, warning и т. д.)
- [ ] Тип/код ошибки
- [ ] Сообщение, понятное человеку
- [ ] Релевантные идентификаторы (user_id, order_id, request_id)
- [ ] Стек-трейс (для неожиданных ошибок)
- [ ] Контекст, приведший к ошибке

### Уровни логирования

Используйте подходящую серьёзность:

- **Error** — что-то не удалось; требует внимания
- **Warning** — что-то тревожное, но не сбой
- **Info** — нормальная работа, заслуживающая упоминания
- **Debug** — подробная информация для диагностики

### Чего не следует логировать

- Чувствительные данные (пароли, токены, персональную информацию)
- Массовые повторяющиеся ошибки (лучше агрегируйте)
- Ожидаемые сбои при нормальной работе (или логируйте на уровне debug)

## Проектирование ошибок

### Типы ошибок

Определите чёткие типы ошибок для разных категорий сбоев:

```text
Ошибки приложения:
  ValidationError — ввод не прошёл валидацию
  NotFoundError — запрошенный ресурс не существует
  ConflictError — операция конфликтует с текущим состоянием
  AuthenticationError — пользователь не аутентифицирован
  AuthorizationError — пользователь не авторизован

Ошибки инфраструктуры:
  NetworkError — сбой сетевого взаимодействия
  TimeoutError — операция превысила лимит времени
  ServiceUnavailableError — зависимость недоступна
```

### Информация об ошибке

Ошибки должны нести полезную информацию:

```text
Структура ошибки:
  type: категория ошибки
  message: описание, понятное человеку
  code: машиночитаемый идентификатор (необязательно)
  details: дополнительная структурированная информация
  cause: исходная ошибка (если это обёртка)
```

## Чек-лист обработки ошибок

- [ ] Ошибки категоризированы (восстановимые/невосстановимые, ожидаемые/неожиданные)
- [ ] Для каждой категории используется подходящая стратегия
- [ ] Ошибки обрабатываются на правильном уровне
- [ ] Проброс ошибок сохраняет полезный контекст
- [ ] Ошибки для пользователей полезны и безопасны
- [ ] Внутренние ошибки подробны и логируются
- [ ] Типы ошибок чётко определены
- [ ] Чувствительная информация не раскрывается

---

## Типичные ошибки обработки ошибок

| Ошибка | Плохо | Лучше |
| --- | --- | --- |
| Проглатывание ошибок | `catch: pass` | Залогировать, затем повторить/пробросить/деградировать |
| Слишком общий перехват | `catch Exception` ловит всё | Ловить конкретные типы, остальные пропускать выше |
| Коды ошибок в возвращаемом | Возврат null/-1 при ошибке | Выбрасывать исключения или использовать типы Result |
| Непоследовательная обработка | Каждый модуль обрабатывает по-своему | Установить соглашения и следовать им |
