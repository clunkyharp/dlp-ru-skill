# Спецификация требований

Спецификация превращает проанализированные требования в точные, проверяемые утверждения. Спецификация — это авторитетный источник истины о том, что будет построено: достаточно точный, чтобы по нему реализовывать и тестировать.

---

## Что делает спецификацию хорошей

Хорошо написанная спецификация:

**Однозначна** — у каждого утверждения одна трактовка. Разные читатели приходят к одному пониманию.

**Проверяема** — можно объективно определить, выполнено ли требование.

**Полна** — вся необходимая информация присутствует. Ни одна критичная деталь не оставлена на усмотрение.

**Согласована** — ни одно требование не противоречит другому. Терминология используется единообразно.

**Прослеживаема** — каждое требование можно проследить назад до потребности и вперёд до реализации и тестов.

---

## Написание формулировок требований

### Структура формулировки

Формулировка требования должна указывать:

- **Субъект** — какая сущность или компонент описывается
- **Действие** — какое поведение или возможность требуется
- **Условие** — когда или при каких обстоятельствах (если применимо)
- **Ограничение** — пределы или качества, которыми должно обладать поведение (если применимо)

### Хорошие и плохие формулировки

| Плохая формулировка | Проблема | Лучшая формулировка | Что улучшено |
| --- | --- | --- | --- |
| «Система должна быть быстрой» | Расплывчато, не проверяется, нет критерия «быстро» | «Результаты поиска должны появляться в течение 2 секунд после отправки запроса» | Конкретное действие, измеримое ограничение, проверяемо |
| «Пользователи могут управлять профилем» | «Управлять» неоднозначно, неясно, какие операции | «Пользователи могут просматривать, редактировать и удалять информацию своего профиля» | Перечислены конкретные операции, выполнимо |
| «Система изящно обрабатывает ошибки» | «Изящно» субъективно, не проверяется | «Когда платёж не проходит, система показывает причину и предлагает повторить попытку или выбрать другой способ оплаты» | Конкретное условие, конкретная реакция, проверяемо |

### Как избегать неоднозначных формулировок

Слова, которые часто вносят неоднозначность:

| Избегайте | Проблема | Используйте вместо |
| --- | --- | --- |
| should/may (следует/может) | Неясно, обязательно ли | «должен» для обязательного или явно укажите необязательность |
| fast/slow (быстро/медленно) | Субъективно | Конкретные пороги времени |
| user-friendly (удобно) | Субъективно | Конкретное поведение интерфейса |
| flexible (гибко) | Расплывчато | Перечислите конкретные поддерживаемые вариации |
| etc., и так далее | Неполно | Перечислите все элементы |
| appropriate (уместный) | Не определено | Укажите критерии |
| reasonable (разумный) | Не определено | Укажите пределы |

## Критерии приёмки

Критерии приёмки определяют, как именно проверить, что требование выполнено. Каждому требованию нужны критерии приёмки.

### Как писать критерии приёмки

Критерии приёмки должны быть:

- **Бинарными** — прошёл или не прошёл, без частичных зачётов
- **Наблюдаемыми** — основанными на видимом поведении, а не на внутреннем состоянии
- **Независимыми** — каждый критерий можно проверить отдельно
- **Конкретными** — без необходимости интерпретации

### Форматы критериев приёмки

**Формат Given-When-Then** — полезен для критериев, ориентированных на поведение.

Требование: «Пользователи могут сбросить пароль»

Критерии приёмки (используйте блоки кода):

```text
Given пользователь на странице входа
When он нажимает "Забыли пароль" и вводит свой email
Then он получает ссылку для сброса пароля в течение 5 минут

Given действующая ссылка для сброса пароля
When пользователь задаёт новый пароль, соответствующий требованиям к сложности
Then он может войти с новым паролем

Given истёкшая ссылка для сброса пароля (старше 24 часов)
When пользователь пытается её использовать
Then он видит ошибку и ему предлагается запросить новую ссылку
```

**Формат чек-листа** — полезен для проверки функции.

Требование: «Страница профиля пользователя»

Критерии приёмки (используйте списки задач):

```text
- [ ] Профиль показывает имя пользователя, email и фото профиля
- [ ] Кнопка редактирования видна только владельцу профиля
- [ ] Фото профиля можно сменить, загрузив изображение
- [ ] Загруженные изображения обрезаются до квадрата и масштабируются до 200x200 пикселей
- [ ] Недопустимые форматы изображений показывают сообщение об ошибке
- [ ] Изменения сохраняются только тогда, когда пользователь нажимает "Сохранить"
```

### Типичные пробелы в критериях приёмки

Убедитесь, что критерии охватывают:

- Счастливый путь (обычная успешная работа)
- Случаи ошибок (что происходит при сбоях)
- Крайние случаи (границы, лимиты, пустые состояния)
- Права доступа (кто может и не может выполнять действие)
- Изменения состояния (какие данные затрагиваются)

## Крайние случаи и условия ошибок

Крайние случаи часто определяют качество ПО. Спецификация должна рассматривать их явно.

### Категории крайних случаев

**Пустые состояния**

- Первый пользователь в системе
- Поиск без результатов
- Список без элементов
- Пользователь без активности

**Граничные условия**

- Максимально допустимые значения
- Минимально допустимые значения
- Ровно на пределах

**Недопустимый ввод**

- Неверный тип данных
- Отсутствующие обязательные поля
- Некорректные данные
- Значения вне допустимого диапазона

**Время и последовательность**

- Одновременные действия
- Операции вне порядка
- Прерванные операции
- Сценарии тайм-аута

**Ограничения ресурсов**

- Загрузка больших файлов
- Много одновременных пользователей
- Заполненное хранилище
- Недоступность сети

### Документирование крайних случаев

Для каждого требования рассмотрите и задокументируйте все крайние случаи.

- Требование: «Пользователи могут загружать фото профиля»

Крайние случаи:

- Фото не загружено: показать аватар по умолчанию
- Файл слишком большой (> 5 МБ): показать ошибку, предложить сжать
- Недопустимый формат (не JPEG/PNG): показать ошибку, перечислить допустимые форматы
- Загрузка прервана: отбросить частичную загрузку, предложить повторить
- Превышена квота хранилища: показать ошибку, предложить удалить старые файлы

## Нефункциональные требования

Нефункциональные требования (NFR) определяют качества, которыми должна обладать система, а не поведение.

### Типичные категории NFR

**Производительность**

- Ограничения времени отклика
- Требования к пропускной способности
- Ограничения на использование ресурсов

**Безопасность**

- Требования к аутентификации
- Правила авторизации
- Потребности в защите данных
- Требования к аудиту

**Надёжность**

- Ожидания по доступности
- Целевое время восстановления
- Требования к сохранности данных

**Масштабируемость**

- Ожидаемый рост числа пользователей/нагрузки
- Требования к ёмкости
- Поведение деградации под нагрузкой

**Удобство использования**

- Требования к доступности
- Поддерживаемые устройства/браузеры
- Потребности в интернационализации

### Как формулировать NFR

NFR должны быть так же точны, как функциональные требования:

Плохо: «Система должна быть безопасной»

Лучше:

- Все пароли должны хешироваться с помощью bcrypt с коэффициентом стоимости 12
- Сессии истекают после 30 минут бездействия
- Неудачные попытки входа ограничены 5 в минуту на один IP
- Все данные при передаче используют TLS 1.2 или выше

Плохо: «Система должна справляться с большим числом пользователей»

Лучше:

- Система поддерживает 10 000 одновременных пользователей
- Время отклика остаётся ниже 500 мс при 80% загрузки
- Система деградирует плавно: операции чтения продолжаются, когда запись ограничивается

## Структура документа спецификации

Организуйте спецификации для ясности и удобной навигации:

```text

1. Обзор
   - Назначение и объём
   - Стейкхолдеры
   - Связанные документы

2. Функциональные требования
   2.1 Область функций A - Требование A.1 - Описание - Критерии приёмки - Крайние случаи - Требование A.2
   ...
   2.2 Область функций B
   ...

3. Нефункциональные требования
   3.1 Производительность
   3.2 Безопасность
   3.3 Надёжность
   ...

4. Ограничения и допущения
   - Технические ограничения
   - Бизнес-ограничения
   - Задокументированные допущения

5. Глоссарий
   - Термины, специфичные для этой спецификации
```

## Чек-лист спецификации

- [ ] У каждого требования есть уникальный идентификатор
- [ ] Каждое требование однозначно
- [ ] У каждого требования есть критерии приёмки
- [ ] Крайние случаи задокументированы
- [ ] Условия ошибок определены
- [ ] Нефункциональные требования включены
- [ ] Зависимости отмечены
- [ ] Допущения задокументированы
- [ ] Терминология единообразна
- [ ] Спецификация внутренне согласована (нет противоречий)
- [ ] Прослеживается до собранных требований

---

## Переход к валидации

Переходите к валидации, когда:

- Все проанализированные требования специфицированы
- Для каждого требования есть критерии приёмки
- Крайние случаи и ошибки рассмотрены
- NFR включены
- Спецификация внутренне согласована
- Вы считаете, что разработчик мог бы реализовать по этому документу

Валидация проверит, что спецификация верна и полна.
