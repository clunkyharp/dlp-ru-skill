# Принципы

Базовые принципы, направляющие решения при разработке. Каждый из них — эвристика: есть контексты, где она работает сильно, и контексты, где её стоит ослабить.

---

## YAGNI — You Ain't Gonna Need It («Тебе это не понадобится»)

### Определение

Не создавайте функциональность, пока она реально не нужна. Не реализуйте возможности на основе догадок о будущих требованиях.

### Когда применять

- Когда хочется добавить параметры или настройки «на всякий случай»
- Когда проектируются абстракции для гипотетических будущих сценариев
- Когда строится инфраструктура под функции, которых ещё не просили
- Когда добавляется гибкость, которой не требует ни одно текущее требование

**Исключения:** добавлять позже непомерно дорого, есть регуляторные требования или подтверждена будущая фаза проекта.

### Пример

```text
Ситуация: строим систему регистрации пользователей

Нарушение YAGNI:
  create_user(name, email, phone, fax, pager, secondary_email,
              preferred_contact_method, timezone, locale, ...)
  "Эти поля могут когда-нибудь понадобиться"

Применение YAGNI:
  create_user(name, email)
  Остальные поля добавляем, когда требования действительно их потребуют
```

### Цена нарушения

Спекулятивные функции:

- Их приходится поддерживать, даже если ими никто не пользуется
- Они усложняют тестирование и документацию
- Они парализуют выбор у будущих разработчиков
- Они часто не совпадают с тем, что реально понадобится

## KISS — Keep It Super Simple («Делай проще»)

### Определение

Если есть несколько решений, удовлетворяющих требованиям, выбирайте самое простое. Усложнять стоит только тогда, когда простые подходы доказуемо не справляются.

### Когда применять

- При выборе между архитектурными подходами
- При проектировании структур данных
- При написании отдельных функций и методов
- При выборе зависимостей и библиотек

**Исключения:** измеренные требования к производительности, уязвимости безопасности, реальная сложность предметной области или массовое дублирование.

### Пример

```text
Ситуация: нужно отслеживать, прошёл ли пользователь онбординг

Сложный подход:
  создать OnboardingStateMachine с состояниями:
    NOT_STARTED, IN_PROGRESS, STEP_1_COMPLETE, STEP_2_COMPLETE,
    PAUSED, RESUMED, COMPLETED, SKIPPED
  с переходами и обработчиками событий для каждого изменения

Простой подход:
  добавить поле: user.onboarding_completed = true/false

Начните с булева значения. Вводите конечный автомат только тогда,
когда требования покажут, что булева значения недостаточно.
```

### Как распознать ненужную сложность

Признаки того, что сложность может быть неоправданной:

- Объяснение того, как что-то работает, длиннее постановки задачи
- Чтобы объяснить одну функцию, нужны диаграммы
- Новички в команде стабильно спотыкаются на одном компоненте
- Крайних случаев в решении больше, чем реальных сценариев использования

## DRY — Don't Repeat Yourself («Не повторяйся»)

### Определение

У каждого фрагмента знания должно быть единственное авторитетное представление в системе.

### Когда применять

- Когда одна и та же бизнес-логика встречается в нескольких местах
- Когда значения конфигурации зашиты в код в нескольких местах
- Когда одинаковые преобразования данных продублированы по кодовой базе
- Когда одни и те же правила валидации существуют в нескольких формах

**Исключения:** код служит разным целям (разойдётся со временем), связанность хуже дублирования, дублирование тривиально или абстракция пока не ясна.

### Пример

```text
Ситуация: две функции форматируют даты — одна для отображения, другая для ответов API

Случайное дублирование (оставить раздельно):
  format_date_for_display(date):
    return дата в формате "January 5, 2025"

  format_date_for_api(date):
    return дата в формате "2025-01-05"

  Выглядят похоже, но служат разным целям и будут развиваться
  независимо. Если заставить их делить код, возникнет связанность.

Осмысленное дублирование (выделить):
  В нескольких местах налог считается по одной формуле:

  order_tax = order.subtotal * 0.08
  invoice_tax = invoice.amount * 0.08
  estimate_tax = estimate.total * 0.08

  Выделяем: calculate_tax(amount) = amount * TAX_RATE
  Ставка налога — это одно знание, и жить оно должно
  в одном месте.
```

### Правило трёх

Терпите дублирование, пока не увидите один и тот же паттерн трижды. К третьему повторению вы уже понимаете, что меняется, а что остаётся постоянным.

## Разделение ответственности (Separation of Concerns)

### Определение

Организуйте код так, чтобы каждый компонент отвечал за одну чётко определённую задачу и как можно меньше знал о внутреннем устройстве других компонентов.

### Когда применять

- При проектировании границ модулей и пакетов
- Когда функция или класс начинает делать «слишком много»
- Когда изменения одной функции постоянно требуют правок в несвязанном коде
- Когда для тестирования компонента нужно сложно настраивать несвязанные системы

**Исключения:** чрезмерная передача данных между компонентами, тесно переплетённые задачи, требования к производительности или простые скрипты.

### Пример

```text
Ситуация: обработка заказа клиента

Смешанные ответственности:
  process_order(order):
    проверить поля заказа
    проверить остатки в базе данных
    рассчитать цены и скидки
    списать оплату через платёжный шлюз
    обновить остатки в базе данных
    отправить письмо с подтверждением
    записать событие аналитики

Разделённые ответственности:
  validate_order(order)           -- логика валидации
  check_inventory(order.items)    -- домен склада
  calculate_total(order)          -- домен ценообразования
  process_payment(order, total)   -- интеграция с платежами
  update_inventory(order.items)   -- домен склада
  notify_customer(order)          -- система уведомлений
  record_analytics(order)         -- система аналитики

  process_order(order):
    оркестрирует перечисленное выше, сама доменной логики не содержит
```

Хорошее разделение ощущается естественно: у компонентов понятные имена, сфокусированные обязанности и минимальные интерфейсы.

## Fail Fast, Fail Clearly («Падай быстро и понятно»)

### Определение

Когда что-то идёт не так, обнаруживайте это как можно раньше и сообщайте достаточно информации для диагностики. Не позволяйте некорректным состояниям распространяться по системе.

### Когда применять

- При проверке входных данных на границах системы
- Когда допущения о данных или состоянии могут нарушиться
- Когда ошибки могут каскадом превратиться в сбои, которые труднее диагностировать

**Исключения:** требуется плавная деградация, есть ожидаемые альтернативные пути или восстановимые ситуации для пользователя.

### Пример

Падение «медленно» (проблематично):

```text
user = fetch_user(user_id)          -- возвращает null, если не найден
orders = fetch_orders(user.id)      -- падает: null.id
// Настоящая ошибка (пользователь не найден) скрыта
```

Падение «быстро» (предпочтительно):

```text
user = fetch_user(user_id)
if user is null:
  raise Error("User not found: {user_id}")
// Ошибка обнаружена сразу и содержит полезную информацию
```

Подробнее о составлении сообщений об ошибках и стратегиях обработки см. [error-handling.md](../development/error-handling.md).

## Принципы SOLID

SOLID — набор из пяти принципов объектно-ориентированного проектирования, способствующих поддерживаемому и гибкому коду. Хотя они возникли в ООП, лежащие в их основе идеи применимы шире.

### Принцип единственной ответственности (SRP)

У модуля должна быть одна и только одна причина для изменения.

Проблема:

```text
UserService:
  - аутентификация пользователей
  - отправка писем
  - генерация отчётов
  - управление подключениями к БД

Изменения в форматировании писем приходится вносить в тот же класс,
который отвечает за аутентификацию.
```

Решение:

```text
AuthenticationService: login/logout
EmailService: отправка писем
ReportGenerator: создание отчётов
DatabaseConnection: подключения к БД

У каждого компонента ровно одна причина для изменения.
```

### Принцип открытости/закрытости (OCP)

Программные сущности должны быть открыты для расширения, но закрыты для модификации.

Проблема:

```text
calculate_discount(customer):
  if customer.type == "gold":
    return 0.20
  if customer.type == "silver":
    return 0.10
  if customer.type == "bronze":
    return 0.05
  return 0

Чтобы добавить новый тип клиента, нужно менять существующий код.
```

Решение:

```text
Каждый тип клиента определяет собственную скидку:
  GoldCustomer.discount() -> 0.20
  SilverCustomer.discount() -> 0.10

Новые типы расширяют поведение, не меняя существующий код.
```

### Принцип подстановки Лисков (LSP)

Подтипы должны быть взаимозаменяемы с базовыми типами без нарушения корректности программы.

Проблема:

```text
У Rectangle есть ширина и высота
Square наследует Rectangle
Square.set_width(w) также устанавливает высоту в w

Код, ожидающий поведение Rectangle, ломается:
  rect = get_rectangle()  // может вернуть Square
  rect.set_width(5)
  rect.set_height(10)
  assert rect.area() == 50  // не выполнится, если это Square!
```

Решение:

```text
Не делайте Square наследником Rectangle. Моделируйте их как отдельные
типы или используйте общий интерфейс Shape, который не обещает
независимых ширины и высоты.
```

### Принцип разделения интерфейсов (ISP)

Клиентов не следует заставлять зависеть от интерфейсов, которые они не используют.

Проблема:

```text
Интерфейс Worker:
  - work()
  - eat()
  - sleep()

RobotWorker обязан реализовать eat() и sleep(), хотя
роботы не едят и не спят.
```

Решение:

```text
Интерфейс Workable: work()
Интерфейс Eatable: eat()
Интерфейс Sleepable: sleep()

HumanWorker реализует все три
RobotWorker реализует только Workable
```

### Принцип инверсии зависимостей (DIP)

Модули верхнего уровня не должны зависеть от модулей нижнего уровня. И те и другие должны зависеть от абстракций.

Проблема:

```text
OrderProcessor напрямую создаёт MySQLDatabase
Переход на PostgreSQL требует менять OrderProcessor

OrderProcessor:
  db = new MySQLDatabase()
  db.save(order)
```

Решение:

```text
OrderProcessor зависит от интерфейса Database
Конкретная база данных внедряется снаружи

OrderProcessor:
  constructor(database: Database)
  database.save(order)

Можно использовать MySQLDatabase, PostgreSQLDatabase или TestDatabase,
не меняя OrderProcessor.
```

### Когда SOLID нужен меньше

- Простые скрипты и одноразовые утилиты
- Прототипы, исследующие предметную область
- Когда накладные расходы на абстракцию превышают пользу
- Кодовые базы, в которых изменений не ожидается

## Композиция вместо наследования

### Определение

Предпочитайте собирать объекты из небольших сфокусированных компонентов, а не строить глубокие иерархии наследования. Наследуйте для отношений «является» (is-a), компонуйте для отношений «имеет» (has-a) или «использует» (uses-a).

### Когда применять

- Когда вы наследуетесь только ради повторного использования кода
- Когда иерархии наследования глубже 2–3 уровней
- Когда подклассы переопределяют большую часть поведения родителя
- Когда нужно объединить поведение из нескольких источников

**Исключения:** настоящие отношения is-a, требования фреймворка, неглубокие стабильные иерархии или случаи, когда полиморфизм упрощает дизайн.

### Пример

Подход через наследование (проблематично):

```text
Bird
  ├── FlyingBird
  │     ├── Sparrow
  │     └── Eagle
  └── NonFlyingBird
        ├── Penguin
        └── Ostrich

А как быть с Duck, которая и плавает, и летает?
А с Penguin, которая плавает, но не летает?
Иерархия запутывается.
```

Подход через композицию:

```text
У Bird есть:
  - FlyingBehavior (CanFly или CannotFly)
  - SwimmingBehavior (CanSwim или CannotSwim)

Duck = Bird + CanFly + CanSwim
Penguin = Bird + CannotFly + CanSwim
Sparrow = Bird + CanFly + CannotSwim

Поведения можно свободно комбинировать без ограничений иерархии.
```

### Признаки того, что нужна композиция

- Вы создаёте подклассы только ради переопределения одного метода
- Вы хотите делить код между несвязанными классами
- В дереве наследования много ветвей «особых случаев»
- Вы боретесь с системой типов, чтобы наследование заработало

## Закон Деметры

### Определение

Метод должен общаться только со своими ближайшими «друзьями», а не с «посторонними». Точнее, метод M объекта O должен вызывать методы только:

- самого O
- объектов, переданных как аргументы в M
- объектов, созданных внутри M
- прямых компонентов O

### Когда применять

- Когда вы видите цепочки вида `a.getB().getC().doSomething()`
- Когда изменения одного класса расходятся по многим другим
- Когда для тестирования приходится массово мокать вложенные объекты
- Когда для понимания кода нужно проследить путь через несколько объектов

**Исключения:** текучие (fluent) интерфейсы, структуры данных для обхода или чрезмерное количество методов-обёрток.

### Пример

Нарушение (залезание внутрь объектов):

```text
process_order(order):
  street = order.customer.address.street
  city = order.customer.address.city
  send_package(street, city)

Этот метод знает внутреннее устройство Customer и Address.
Изменения в Address сломают этот код.
```

С соблюдением закона Деметры:

```text
process_order(order):
  shipping_address = order.get_shipping_address()
  send_package(shipping_address)

Order выдаёт то, что нужно. Внутренняя структура скрыта.
```

Альтернатива («Tell, Don't Ask»):

```text
process_order(order):
  order.ship()

Ещё лучше: скажите заказу отправить себя самому, а не
извлекайте данные, чтобы выполнять отправку снаружи.
```

### «Tell, Don't Ask» («Говори, а не спрашивай»)

Родственный принцип: вместо того чтобы запрашивать у объекта данные и потом действовать, скажите объекту, что нужно сделать. Это естественным образом следует из закона Деметры.

Спрашиваем (нарушение):

```text
if customer.account.balance >= amount:
  customer.account.balance -= amount
```

Говорим (соблюдение):

```text
customer.charge(amount)
// Клиент сам знает, как работать со своим счётом
```

## Совместное применение принципов

Эти принципы иногда вступают в противоречие друг с другом:

- **YAGNI и SOLID** — SOLID поощряет абстракции и интерфейсы, а YAGNI предостерегает от спекулятивного проектирования
- **DRY и KISS** — устранение дублирования может внести сложные абстракции
- **Композиция и KISS** — композиция добавляет косвенность; иногда наследование проще
- **Закон Деметры и практичность** — строгое следование может породить избыток методов-обёрток
- **Fail Fast и KISS** — исчерпывающая обработка ошибок усложняет код

Когда принципы конфликтуют, задайте себе вопросы:

1. **Какова цена ошибки?** Если ошибку дёшево исправить, предпочитайте YAGNI и KISS. Если дорого — вкладывайтесь в разделение ответственности и обработку ошибок.
2. **Чего на самом деле требует задача?** Пусть балансом управляют реальные, а не гипотетические потребности.
3. **Что упростит изменение этого кода?** Принципы существуют ради поддерживаемости. В сомнении спросите, какой выбор облегчит будущие изменения.

Подход к разрешению таких компромиссов см. в [decision-making.md](decision-making.md).
